BrainMCP for many people

A proposal to turn one person's brain into a system where every person gets their own brain, shares parts of it with others, and works only through MCP. Yash stays super admin and is also an ordinary user.

Approved and built · 2026-10-05 · repo Yash121l/BrainMCP

Short version

  • Today a key is a slice of your brain. A friend with a key can read or write the paths you picked, but has no brain of their own and can't create projects, keys or shares without an admin key.
  • The fix is to add people as a first-class idea. A user owns one or more spaces. A space is a brain with its own projects, notes, decisions, sessions, skills and rules. Everyone gets a personal space. Spaces and single projects can be shared with other users as viewer or editor.
  • Every key belongs to a user and can never do more than that user. Users mint and revoke their own keys, create projects and share them through new MCP tools, so nobody needs your admin key again.
  • Each space lives in its own Durable Object with its own SQLite database. Two people's notes are never rows in the same table, so a missed WHERE clause can't leak one person's brain into another's.
  • Your brain stays exactly where it is, git-backed in Yash121l/brain. Friends' spaces are hosted. Their notes never land in your GitHub repo or on your Mac.
  • Only a space's owner or admins can publish content that binds an agent: skills, skills.md, rules. Everything else an agent reads is labelled as data with its author. That closes the main prompt-injection path once other people can write.
  • Every write, share, key change, denied request and super-admin access goes into a hash-chained audit log. You can see everything. Each user can see their own trail, including any time you looked at their data.

Status, 2026-10-05: built and deployed

Phases 0 to 3 and most of phase 4 are live. Where the build differs from this page:

  • Your @yash space keeps its index in the existing D1 tables instead of moving to a Durable Object. No other user's notes are in D1, so the isolation argument still holds, and your index, reindex and webhook paths stay exactly as they were.
  • Not built yet: passkeys for the web UI and OAuth consent, the GitHub App swap (it needs you to create the app in GitHub), and an R2 retention lock on the audit archive (a bucket setting in the dashboard). Daily audit archives to R2 and the hash chain itself are live.

1. What exists today

One Worker, one D1 index, one GitHub repo, one owner. Keys carry a role (read, write, admin) and a list of path prefixes or project:<slug> scopes. It works well for one person across many machines and many projects. It breaks down for a second person in four places.

Where it breaks for a second person

  1. A friend has no brain of their own. Anything they write lands inside your vault, under paths you had to pre-authorize.
  2. Creating a project, minting a key, or changing scopes needs an unscoped admin key, which is your whole brain.
  3. There is one skills.md, one decisions.md and one default skill row for everyone. Anyone with write access to those paths changes what every session treats as binding.
  4. No record of who did what. Commits are all authored by the Worker's GitHub token.

What is already solid and stays

  • Hashed keys with lineage: sessions and OAuth tokens die with their parent key, and narrowing a key narrows its tokens.
  • Canonical-path checks, SQL-side scope filters, PKCE S256 only, exact redirect URIs.
  • git as source of truth for your brain, with D1 as a rebuildable index.
  • The one-call save and get_context bootstrap.
  • 48 passing tests on a node:sqlite fake D1, which the new permission tests extend.

The rule that keeps this safe: a key is a subset of a user, and a user's access is the union of their memberships and shares. Revoke a share and every key and connector token that user holds loses it on the next request, because access is computed live, never copied onto the key.

3. Architecture

Two planes. The control plane is one D1 database that knows who exists and who may do what. The data plane is one Durable Object per space, each with its own SQLite database holding that space's notes, link graph and full-text index. The Worker in the middle is the only thing that talks to both, and every request goes through one authorize function before it reaches any space.

Why a Durable Object per space instead of a space_id column in D1

The cheaper option is one D1 database with a space_id on every row. It would work, and today's code already filters every query by scope. But one forgotten filter in one future query leaks a person's brain to everyone, and that bug class is exactly what the last audit spent most of its time on. With a database per space, the Worker picks which database to open after authorization, and a query inside it can only ever see that space. The cost is a fan-out when someone searches across several spaces they can read, which is a handful of parallel calls for a few users. SQLite Durable Objects are on the Workers free plan (100k requests a day, 100k rows written a day, 5 GB stored in total), support FTS5, and keep 30 days of point-in-time recovery.

Your brain does not move

@yash is a git-backed space bound to Yash121l/brain. GitHub stays the source of truth, Obsidian and the launchd sync keep working, and the webhook and nightly reindex now fill the @yash Durable Object instead of the shared D1 notes table. Friends' spaces are hosted, so their notes never pass through your repo, your GitHub token, or your Mac.

4. Data model

Inside each space's Durable Object the tables are today's notes, links and fts, plus note_versions for hosted spaces, which gives them git-like history without git. Every note written by the server gets author: and updated_by: frontmatter that the server sets, so a client can't forge authorship.

5. Permissions

One function decides everything: authorize(principal, action, resource). It replaces today's mix of allowed, canWrite and isRootAdmin checks spread across files. A test suite walks the full matrix below, one row per role and action, so a regression fails CI instead of shipping.

There are five actions. read and write are ordinary notes. publish covers content that binds an agent: skills/**, vault/skills.md, vault/rules/**. manage covers members, shares and keys. admin covers users and the whole system.

6. Flows

Onboarding a friend, MCP only

  1. You call admin_create_user with handle priya. The server creates the user and a personal hosted space @priya seeded with templates and a skills.md whose default row points at @system skills, and returns a one-time invite link that expires in 72 hours.
  2. Priya opens the link. It shows her first key exactly once, with cap manage, limited to her own spaces. In phase 4 she registers a passkey here instead and mints keys from that.
  3. She adds the MCP server to Claude Code with that key, or adds the claude.ai connector and signs in on the consent page.
  4. get_context now returns her space. create_project makes a project, save writes to her space, create_key gives her a narrower key for her VPS. None of this touches your brain or needs you.

Sharing a project

You call share with project @yash/brainmcp, user @priya, role editor. Priya's next get_context lists it under shared_with_me. When she works on it, her session logs and decisions are written into your space under that project with author: priya, so both of you see one history. She can't edit your skills, rules or any other project. You can revoke it with unshare and her keys lose it on the next request.

You as super admin

Day to day you use an ordinary key on @yash and behave like any user. For admin work you mint a short-lived super key and call the admin_* tools: create, suspend or delete users, set quotas, read any space, query the full audit log. Suspending a user kills all their keys, sessions and connector tokens at once, because every credential's lineage now ends at a user whose status is checked on each request.

7. Skills and prompt injection

Skills are the most dangerous content in the system, because get_context tells the agent to obey them. Today any write key whose scope covers skills/, vault/skills.md or vault/rules/ can change what every future session treats as mandatory. That is tolerable while every writer is you. With other people writing, it becomes the obvious attack. The design splits content into instructions and data, and only a narrow set of people can produce instructions.

  • An editor on your shared project can write notes and sessions there. They can't touch skills.md, rules or skill files, because those need publish, so they can't plant instructions in your sessions.
  • When Priya works on your project, your project's skills and rules apply to her session, labelled source: @yash. She accepted the share, so she trusts you for that project. Your sessions never pick up anything from her space.
  • The hash on each must-load skill lets a client notice when binding content changed since the last session.
  • The skills installer and get_skill serve supporting files too, such as references/*.md, so a skill works for someone with MCP alone and no repo access.

8. Security and encryption

One honest limit

The live search index inside each space's Durable Object holds plaintext, because full-text search has to read the words. It is protected by Cloudflare's at-rest encryption, by the space being its own database, and by authorize running before any query. Application-level encryption covers history, backups, exports and personal data, and gives a real delete. A fully end-to-end encrypted "sealed project", where only the user's agent holds the key and the server can't search it, is possible later as an opt-in. I don't recommend it as the default because it removes search and the super admin's ability to audit content, which you asked for.

9. New MCP tools

Everything a user needs is an MCP tool, so nobody needs the web UI or repo access. Existing tools keep their names and gain an optional space argument. Project names accept @space/slug. A bare slug resolves to your own space first, then to projects shared with you, and an ambiguous name returns the choices instead of guessing.

Every user

  • whoami: user, spaces, roles, shares, the calling key's cap
  • create_project, list_projects
  • share, unshare, list_shares
  • create_key, list_keys, revoke_key, own keys only, never wider than yourself
  • create_space, add_member, remove_member
  • publish_skill, set_skills, needs publish
  • audit_log: your own actions, actions on your spaces, and any super-admin access to your data
  • export_space: a short-lived signed download link

Super admin, super key only

  • admin_create_user: returns a one-time invite link
  • admin_list_users, admin_set_quota, admin_set_flags
  • admin_suspend_user, admin_restore_user
  • admin_delete_user: drops the space and destroys its DEK
  • admin_audit: the whole log, with filters
  • admin_read: read any space, recorded as super.read

Users with the can_invite flag can also invite people into their own team spaces, which creates an account with a personal space.

Left for the multi-user build, because they need it

  • Telemetry ingest records no principal. Any write key can append to anyone's session and fill the shared 20k-row buffer. The fix needs a key_id column, which is a schema migration CI can't run, so it goes into phase 1.
  • Editing a note's frontmatter to project: alpha still widens what project:alpha keys can write. Binding paths are now safe from this. The real fix is project membership in a table, which is phase 1.
  • One shared decisions.md and one global default row. Section 7's per-space layers replace both.
  • The nightly hygiene snapshot is unscoped and /health is public. It only shows counts, but it should be per user once there are several.

Things for you to change in the vault

  • no-comments is must-load in skills.md but its own frontmatter says disable-model-invocation: true. That tells every session to run a user-invoked procedure unprompted. I'd drop the ! and invoke it as /no-comments, which also saves about 760 tokens a session.
  • vault/projects/pulse.md is 97k characters, 72k of it in "Current state". It's clipped to 8k in get_context now, but trimming it helps every tool that reads it.
  • portfolio, freelance, harness-hackathon and angel-os have an empty project:, so get_context never finds their session logs.

12. Decisions I need from you

  1. Where friends' data lives. I recommend hosted spaces, so it never enters your GitHub repo. The alternative is folders inside Yash121l/brain, which is faster to build but syncs everyone's notes to your Mac and your Obsidian.
  2. Super-admin reads. I recommend that you can read anything, and that each read shows up in that user's audit log. The alternative is silent access, which I'd advise against once friends trust the system with their notes.
  3. Who can invite. I recommend that only you can create users at first, with a per-user can_invite flag you can switch on for people who run team spaces.
  4. Web UI for friends. I recommend MCP only through phase 3, keeping the web UI for you. The UI already speaks the same API, so opening it to others later is mostly permission work.
  5. Free tier. The design fits the Workers free plan for a handful of users. If more than about ten people write daily, the 100k rows written a day limit becomes the constraint, and the $5 Workers paid plan lifts it.

Once you answer these, I start with phase 0, which is already done in this branch, and phase 1.
