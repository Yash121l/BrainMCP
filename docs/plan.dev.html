Plan · BrainMCP · 2026-10-05 · Written in ASD-STE100 Simplified Technical English

BrainMCP becomes the hub for all AI work

One endpoint for every harness. It supplies memory, all your tools and all your models. You control which agent on which machine can use which account.

Summary
  • BrainMCP adds four parts: a tool router, a credential vault, a policy engine and a model gateway. All parts stay on Cloudflare.
  • Each upstream account is a connection. Three Figma accounts are three connections: figma_personal, figma_rtp, figma_acme.
  • Each agent on each machine has its own key. Rules decide which key can use which connection and which tool. The default is deny.
  • Agents see about 10 tools. They find all other tools through search_tools. This keeps tool selection accurate when there are hundreds of tools.
  • One bundle, the BrainPack, installs memory, skills, hooks and tools into every harness on a machine. A brain CLI does the installation.
  • No surveyed product has accounts as first-class objects, attenuating key trees or brain-linked audit. BrainMCP can own this space.

1. Decisions

You told me to decide all open questions. Each decision below follows from the requirements, the research or a hard limit. You can change any of them.

Q1
Audience
You on many machines, plus friends. The design must also work as a product later.
Multi-user spaces exist. Every new table has a space_id and an owner. Thus a product needs no schema change.
Q2
Scope
Memory, MCP router for all tools, and a model gateway. No chat UI.
T3 Code and the harnesses already supply chat. A chat UI adds work and no new capability.
Q3/Q10
Who a rule applies to
A call has four nested identities: user → machine → agent → key. A key gets the intersection of the grants on all four. A child key cannot exceed its parent.
Super sets all rules. A space admin sets rules for the connections of that space. A user sets rules for their own keys and connections.
Q4
Multiple accounts
The account is a connection ID, for example figma_rtp. Agents call call_tool({connection, tool, args}). list_connections and each search result show the account email, workspace and scopes.
A key that is pinned to one connection can also see direct names, for example figma_rtp__get_design. Emails are not in tool names: Gemini cuts names at 63 characters, and emails can change.
Q5
Where upstream servers run
Remote HTTP servers: the Worker calls them directly. Local stdio servers: a small bridge on each machine. Cloud stdio servers: Cloudflare Containers, only if necessary.
Workers cannot run stdio processes. The bridge reaches the Worker through Cloudflare Tunnel.
Q6
Credentials
BrainMCP holds them. A new VAULT_KEK wraps one key for each credential. No tool, log or admin route returns a token.
The MCP spec forbids token passthrough. The vault design is in section 10.
Q7
Research width
Eight research agents covered memory, gateways, hosted tool platforms, Cloudflare, model gateways, security, tool discovery and harness plugins.
Section 3 has the results.
Q8/Q17
Where this plan lives
On postplan.dev, and as docs/plan.dev.html in the repo.
You chose postplan.dev.
Q9
Platform
Cloudflare stays. Section 19 lists each Cloudflare limit and the external service that fills it.
Agents SDK, Code Mode, Dynamic Workers, AI Gateway and Vectorize supply most parts.
Q11
Approvals
The tool call returns input_required. You approve on the web console or from a phone push. The harness then sends the call again.
MCP elicitation does not work in all harnesses. An out-of-band channel works everywhere. The agent cannot approve its own request.
Q12
Sharing accounts with friends
Connections are private by default. You can share one connection with one person, for named tools only. A team space can own a connection.
The friend never receives the token. The friend uses the connection through your vault, and the audit log records the friend's name.
Q13
Tool discovery
Three tiers: about 10 tools always listed; all other tools found through search_tools; run_code for multi-step work.
Only Claude Code reloads tool lists during a session. Codex and ChatGPT do not. Thus discovery must happen on the server.
Q14
Plugin
A BrainPack: connections, skills, hooks, policies and rules in one bundle. It uses the Agent Plugins 1.0 layout. Adapters convert it for each harness.
Phase 6 adds code plugins that run in Dynamic Workers.
Q15
Memory
Hybrid search (FTS5 + Vectorize), fact versions, token budgets and consolidation proposals. Automatic fact extraction is opt-in and goes to a separate "inferred" layer.
Readable notes stay the source of truth. An LLM must not edit your notes without your approval.
Q16
Model gateway
A thin BrainMCP layer in front of Cloudflare AI Gateway. It checks the key, applies a budget and records cost. BrainMCP also calls models for its own memory work.
Do not build provider adapters. Do not use LiteLLM: it had a supply-chain attack and an MCP auth CVE in 2026.

Parts to keep and reuse
  • Scoped API keys in a tree. A revoked key revokes all its children.
  • OAuth 2.1 with DCR and PKCE for claude.ai connectors.
  • Per-space Durable Objects with envelope encryption (BRAIN_KEK).
  • Hash-chained audit log in AuditDO, archived to R2.
  • Spaces, members, shares and invites.
  • Skills library with must_load and on_demand layers.
  • Web console (React) with keys, sharing and admin tabs.
Gaps to close
  • Transport is POST only. There are no resources, prompts or structured results. Results are JSON text.
  • No machine or agent identity. "One key per machine" is a convention only.
  • No per-tool permission. Access uses role, path scope and membership only.
  • get_context labels text from lower-trust writers as authoritative. This is a prompt-injection path.
  • Read-only keys can use all of the owner's GitHub API quota.
  • Installers need python3 and write a plaintext credentials file.

4. White space: what no product does

Accounts as objects
A connection has a discovered identity (email, workspace), a label and a default per project. Gateways only register the same server many times.
Attenuating key trees
You give a friend or a sub-agent a child key. The key can only narrow: one account, read tools, 7 days. All gateways use flat roles.
Share use, not the secret
A friend uses your Affinity connection through your vault. The token stays in your Durable Object.
Context routing
get_context knows the project. The project selects the account: work Figma for project X. Personal Gmail never.
Edge-native
One Worker. No Docker, no Kubernetes. All serious gateways need one of the two.
Brain-linked audit
Each tool call joins to the session, the decision and the project. One query answers: which agent, which machine, which account, what, and why.

6. Identity and policy model

Default rules (always on)

  1. Deny all calls that no rule permits. A forbid rule always wins.
  2. Hide and block a tool when its manifest hash is not approved.
  3. A critical tool always needs approval.
  4. An egress tool needs approval when the session has read untrusted data and private data. This stops the "lethal trifecta".
  5. Agents cannot connect accounts, revoke access, mint keys or change rules. Only a human in a browser session can do these.
  6. Remove denied tools from tools/list and from search_tools results. Do not show a tool that the agent cannot call.

Who can write rules

RoleCan write rules forCannot
SuperAll spaces, all connections, global defaultsRead a token in plaintext
Space adminConnections that the space owns, and member keys in that spaceChange global defaults
UserOwn machines, own agents, own keys, own connections, own sharesGrant more than their own grant
Agent keyNothingAny change to rules, keys or connections

Example rules

// Coding agents on laptops may read from the work GitHub account.
permit(principal is Agent, action == Action::"call", resource is Tool)
when { principal.tags.contains("coding") && context.machine.tags.contains("laptop")
    && resource.connection == Connection::"github_work" && resource.risk == "read" };

// The mail agent may search and draft in RTP Gmail. It may not send.
permit(principal is Agent, action == Action::"call", resource is Tool)
when { principal.name == "mail" && resource.connection == Connection::"gmail_rtp"
    && ["search_threads","get_thread","create_draft"].contains(resource.name) };

// Critical tools need approval.
forbid(principal, action == Action::"call", resource is Tool)
when { resource.risk == "critical" } unless { context.approved };

// Egress after untrusted + private input needs approval.
forbid(principal, action == Action::"call", resource is Tool)
when { resource.egress && context.taint.contains("untrusted") && context.taint.contains("private") }
unless { context.approved };

The console writes these rules from simple forms. You do not need to write Cedar by hand.

How BrainMCP selects the account

  1. When the call names a connection, BrainMCP uses that connection. The policy must permit it.
  2. When the call names only a service, BrainMCP uses the key's pinned connection for that service.
  3. When there is no pin, BrainMCP uses the project default from get_context.
  4. When there is no default, BrainMCP returns the list of permitted connections. The agent must select one.
  5. BrainMCP never selects a shared connection automatically.
  6. When BrainMCP sees two connections with the same upstream identity, it shows a warning in the console.

    Tool naming

    • Connection IDs: {service}_{label}, lowercase, [a-z0-9_], label of 12 characters or fewer.
    • Direct names, when used: figma_rtp__get_design. Do not use . or /. Some provider APIs do not accept these characters.
    • Account identity goes in list_connections, in search results and in _meta["brainmcp/connection"]. A short suffix goes in the description, for example "(Figma: RTP Global)".
    • Annotations (readOnlyHint, destructiveHint, openWorldHint) give the default risk. You can override the risk in the console.

    10. Credential vault

    • Only the internal invokeUpstream(connection, tool, args) function can decrypt. No MCP tool or admin route returns a token. Super sees only metadata and fingerprints.
    • One ConnectionDO for each account serializes the token refresh. This prevents reuse of a rotated refresh token.
    • Connect flow: a /connect page with a fresh browser login. The page checks that the user who opens it is the user who started the flow. It uses PKCE, server-made state and an RFC 9207 iss check.
    • API keys for services go into the web console only. They never go through chat or form elicitation.
    • Revocation deletes the DEK (crypto-shredding). BrainMCP also calls the upstream revocation endpoint when one exists.
    • KEK rotation re-wraps the DEKs in a background Workflow.
    • Tests search every response and log line for secrets. A test fails when it finds one.

    11. Safety: taint, approvals, poisoning

    Tool pinning
    At approval, BrainMCP hashes name, description, input schema and annotations. When an upstream changes a hash, BrainMCP hides the tool and asks you to approve again.
    Output envelope
    Upstream output goes back as labeled untrusted data, with a size cap. Workers AI scans it for prompt injection. A match adds a flag, and the policy can block on the flag.
    get_context fix
    Only rules from the owner or an admin are "binding". All other text has a label for the trust tier of its author. Tool output is never binding.

    Risk tiers

    TierExamplesDefault for agent keys
    readget_design, search_threads, list_issuesAllow when a rule grants the connection
    writecreate_draft, post_comment, create_issueAllow when a rule grants write. Audit with arguments hash.
    destructivedelete_file, archive_channelDeny. A rule can change it to approval.
    criticalsend email, merge to main, payment, bulk deleteAlways approval

    12. Memory upgrades

    1. Hybrid search. Add Vectorize as a second channel. Use one namespace for each space. Store IDs only in vector metadata. No LLM runs at query time.
    2. Generated questions. When a note changes, Workers AI writes 3 to 5 questions that the note answers. BrainMCP embeds them with the chunk.
    3. Fact versions. Decisions and facts get valid_from, valid_to and superseded_by. get_context returns current facts only.
    4. Token budget. get_context and search accept max_tokens.
    5. Consolidation proposals. A weekly Workflow finds duplicate topics and stale facts. It writes proposals. You accept or reject each proposal.
    6. Opt-in extraction. save can propose facts from the session. They go to an "inferred" layer with a label. They do not change notes.
    7. Scope keys. Each write records machine and agent from the key. You can ask "what did Codex on the MacBook learn?"
    8. Revocation. When you revoke a share, BrainMCP deletes the related vectors from the namespace of the friend.

    13. Model gateway

    BrainMCP adds three routes. Each route uses the same BrainMCP key as MCP.

    • /llm/anthropic/*: Anthropic Messages, for Claude Code and the Agent SDK.
    • /llm/openai/*: Responses and Chat Completions, for Codex, Cursor and OpenCode.
    • /llm/gemini/*: Gemini native, for Gemini CLI.

    The shim checks the key and the budget. It sends the request to AI Gateway with cf-aig-metadata (user, machine, agent, session). It reads usage from the response and writes the cost to the audit log.

    Limits
    • Subscription traffic (Claude Max, ChatGPT Plus) mostly cannot go through a third-party URL. The gateway helps API-key traffic.
    • Claude Max can pass through when Claude Code sends it, with the BrainMCP key in a separate header. Vercel documents this pattern. Anthropic changed its policy five times in 2026. Test it before you use it.
    • Prompt logs are off by default. BrainMCP stores tokens, cost, model and key ID only.
    • Require BYOK. Do not let AI Gateway fall back to Unified Billing.
