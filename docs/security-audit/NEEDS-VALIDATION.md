# Needs validation

Prioritised leads with no severity. Each one names the exact missing fact and a safe way to settle it. The owner-observed checks are read-only or run on a throwaway deployment. None asks for audit traffic against production.

## 1. get_context puts text from lower-trust scoped writers into the owner's context for other projects, using labels the writer chooses and no writer provenance, under server framing that calls the response authoritative

`brainmcp:get_context:unscoped-writer-text-in-authoritative-response`

The MCP initialize instructions (src/index.js:150) tell every client that the get_context response 'is authoritative for this session'. Every get_context call also carries the hint 'Binding rules above are MANDATORY for this project' (index.js:384-386), including calls with no project. Three fields in that response come from text a lower-trust scoped writer controls, and two of them are picked by labels that writer chooses. (1) recent_sessions[].summary is chosen by the frontmatter fields type='session' and project=<slug> (index.js:375), not by path. A write key scoped project:alpha may write anywhere under vault/projects/alpha/ (auth.js:64). It can create a note there with type: session and project: [[projects/beta]], and that summary then appears in the owner's get_context(beta). A key scoped vault/logs/ can do the same through append_session_log(project=beta). (2) recent_decisions[] is chosen by a substring match on [[projects/<slug>]] (index.js:371). log_decision accepts any project from any writer that can write vault/logs/decisions.md (index.js:468-476), so a vault/logs/ key can place blocks of up to 500 chars in the owner's beta context. (3) active_projects[].next comes from every active project note and is included in every get_context call (index.js:358). This is the weakest of the three: it is the designed cross-project table, and each row carries its true source path. No field identifies the writing key or principal. Decision blocks carry no source marker at all. Session rows show only the source file path, which reveals the forged session's real location (vault/projects/alpha/...) but not the writer. Nothing marks these fields as data rather than instructions. The boundary does hold in some places: binding_rules is selected by the fixed path vault/rules/<slug>.md (index.js:363-364), and skills.must_load bodies come from the skills/ config and skills/<name>/SKILL.md paths (skills.js:130-141). A forged type: rules, project: beta note under vault/projects/alpha/ did not reach binding_rules. An independent local harness (fake D1, in-memory GitHub, worker.fetch('/mcp')) confirmed the following. Both dummy writers were refused get_context(beta), read_note and update_note on vault/projects/beta.md. Each then wrote only inside its own scope. All four dummy markers reached the root owner's get_context(project=beta). The alpha next: marker and the decision marker also reached get_context() with no project. Whether a consuming model treats this text as instructions was not observed and cannot be observed here.

**Claimed root cause.** get_context builds one response that INSTRUCTIONS (index.js:150) declare authoritative. It fills recent_sessions and recent_decisions using project labels the writer controls: frontmatter type/project parsed from file content (parse.js:97-98) and a caller-chosen log_decision project matched as a substring (index.js:92-96, 371, 468-476). Nothing checks that the source path, or the key that wrote it, belongs to the requested project. Reads are filtered only by the reader's scope (allowed() at index.js:358 and 377), and the owner's root scope passes everything. The response records no per-field provenance, such as the writing key or a trusted/untrusted label. It also does not separate these data fields from binding_rules and skills, the fields meant to be followed. As a result, a writer scoped to project:alpha or to vault/logs/ can place text in the owner's full-scope agent context for project beta, a project that writer cannot read or write, inside a response the server calls authoritative.

**Trace.**
1. **entrypoint** `src/index.js:479` (callTool update_note): A write key scoped ['project:alpha'] passes canWrite and allowed() for vault/projects/alpha.md and anything under vault/projects/alpha/, because expandScopes adds those prefixes (auth.js:64). It writes next: on alpha.md, or a new note with type: session, project: [[projects/beta]] and a summary of its choosing.
2. **propagation** `src/index.js:468` (callTool log_decision / append_session_log (index.js:453)): Parallel entrypoint: A write key scoped ['vault/logs/'] calls log_decision with project=beta. This appends a decisionBlock (index.js:92-96) whose '- **Project:** [[projects/beta]]' line it chose. The same key can call append_session_log(project=beta), which writes a session note with project: "[[projects/beta]]" (index.js:67) under vault/logs/sessions/.
3. **propagation** `src/parse.js:98` (parseNote via upsertLocal): type and project are copied verbatim from the written frontmatter (parse.js:97-98) and stored in the D1 notes row. Nothing records which key or principal wrote the note.
4. **propagation** `src/index.js:375` (get_context recent_sessions): Sessions are selected by type = 'session' AND project = ? from the stored row, not by path ownership. Line 377 filters only by the reader's allowed(); root passes everything. Each summary is returned verbatim, with its path.
5. **propagation** `src/index.js:371` (get_context recent_decisions): Decision blocks are chosen with b.includes(`[[projects/${slug}]]`), a label the writer set. The last 10 blocks, up to 500 chars each, are returned with no source marker.
6. **propagation** `src/index.js:358` (get_context active_projects): Every active project note's next: (up to 400 chars) appears in every get_context response, whatever slug was requested. Rows are filtered only by the reader's scope and carry the source path.
7. **sink** `src/index.js:150` (initialize INSTRUCTIONS + get_context hint (index.js:384-386)): The consuming agent is told the get_context response is authoritative for the session. The hint on every call says 'Binding rules above are MANDATORY for this project'. The writer-controlled fields sit beside binding_rules and skills in the same object, with no trusted/untrusted marker and no writer identity.

**Evidence.**
- `src/index.js:150`: INSTRUCTIONS: 'Its response is authoritative for this session: binding_rules are mandatory, skills.must_load bodies apply without being asked...'
- `src/index.js:385`: The hint 'Binding rules above are MANDATORY for this project.' is added on every get_context call, including calls without a project slug.
- `src/index.js:375`: The recent_sessions SQL selects WHERE type = 'session' AND project = ?. Both values come from file content, not from path ownership or the writer's key.
- `src/index.js:371`: recent_decisions is filtered with b.includes(`[[projects/${slug}]]`) or b.includes(`**Project:** ${slug}`). The label is the caller-chosen log_decision project.
- `src/index.js:358`: active_projects is filtered only with allowed(p, r.path) for the reader. Every active project's next: appears in every response.
- `src/index.js:364`: Boundary that holds: binding_rules is read from the fixed path vault/rules/<slug>.md. A forged type: rules, project: beta note under vault/projects/alpha/ did not reach it in the local harness.
- `src/parse.js:98`: project = normalizeProject(fm.project), and type = fm.type on line 97, both taken directly from the writer's frontmatter.
- `src/auth.js:64`: A project:<slug> scope expands to the vault/projects/<slug>.md and vault/projects/<slug>/ prefixes, so that writer can create any note under the folder with any type/project frontmatter.
- `src/index.js:468`: log_decision needs only canWrite plus allowed('vault/logs/decisions.md'). args.project is not checked against the caller's scope.
- `src/index.js:462`: The append_session_log error text 'key needs the vault/logs/ prefix' shows that vault/logs/-scoped write keys are an intended key shape.

**Blockers.**
- Model compliance is not observable here. No model may be called, so it is unknown whether a consuming client (Claude Code, a claude.ai connector, Codex) acts on recent_sessions.summary, recent_decisions or active_projects.next text as instructions because of the server's 'authoritative'/'MANDATORY' framing. The code-level label forgery and the cross-project delivery are reproduced locally. Real impact depends on this unobserved behaviour.
- Deployment fact: whether the operator actually issues write keys scoped project:<slug> or vault/logs/ to principals less trusted than the owner. The source supports and points to both: project grants in KeysView/expandScopes, and the append_session_log error text 'key needs the vault/logs/ prefix'.

**Local plan.** Run agents/verify-26/artifacts/v26_getcontext.mjs through tools/sbx.py (Node 26, no network, fake D1 and in-memory GitHub, dummy keys bk_v26_alpha ['project:alpha'] and bk_v26_logs ['vault/logs/']). Expected on the current source: six 'forbidden' baseline lines; 'RESULT owner beta context contains <alpha next | alpha-forged beta session | logs-key beta decision | logs-key beta session>: true'; 'RESULT forged rules reached binding_rules: false'; 'RESULT key name/id present anywhere: false'; 'RESULT forged session row path exposes true location: true'; 'RESULT owner get_context() contains alpha next: true | decision: true'. ## 2. Full repo tarball is decompressed into one unbounded in-memory buffer, so a project-scoped writer can grow it to break nightly reindex and the skills installer for everyone

`github.js:fetchRepoTar:unbounded-decompressed-tar-buffer`

fetchRepoTar gunzips the whole GitHub tarball of the brain repo's branch head into a single ArrayBuffer with no size cap, and tarEntries walks that buffer. Every file in the tree is held in memory, including non-.md blobs that are never indexed. Three paths share this buffer: the nightly cron fullReindex, POST /admin/reindex, and GET /skills/install.sh, which any authenticated principal can call. No MCP write tool limits content size. A write-role key scoped only to project:<slug> can therefore commit large non-.md files under vault/projects/<slug>/. These files are not indexed, so no D1 row limit applies, and the writer can keep adding them until the decompressed tree is bigger than the Worker isolate memory. From then on, every nightly reindex fails. The hygiene snapshot and telemetry rollup in the same cron invocation are skipped, and /skills/install.sh fails for every key holder. This lasts until the owner removes the files from the branch head. Recovery is easy: delete the files at HEAD. The D1 index is not wiped, because the DELETE runs only after parsing. Webhook incremental indexing, which reads only .md files, keeps working. The writer's scope is one prefix; the effect is brain-wide. Whether the deployed Worker actually exceeds its memory limit, and how many writes that takes, depends on platform limits that are not in the source.

**Claimed root cause.** src/github.js:117-118 pipes the tarball body through DecompressionStream and materialises all of it with new Response(gunzip).arrayBuffer(). It has no byte counter and no maximum decompressed size. tarEntries (src/github.js:123) takes the complete buffer, so it cannot stream or stop early. The MCP write paths (update_note src/index.js:479-484, save_session, save) have no per-file or aggregate content-size limit. A project:<slug> scope grants writes to any file type under vault/projects/<slug>/ (src/auth.js:64).

**Trace.**
1. **entrypoint** `src/index.js:479` (callTool update_note (via POST /mcp tools/call)): A write-role managed key scoped to project:alpha passes canWrite (:480) and allowed (:481) for any path under vault/projects/alpha/. Its args.content of any length is committed through putFile at :483. No length check exists.
2. **propagation** `src/auth.js:64` (expandScopes): project:<slug> expands to the prefixes vault/projects/<slug>.md and vault/projects/<slug>/. allowed() is a plain startsWith check, so non-.md blobs in that folder are writable. upsertLocal skips them because isIndexable requires .md, so they never reach D1.
3. **propagation** `src/index.js:899` (scheduled -> fullReindex): The nightly cron calls fullReindex (:26-28), which calls fetchRepoTar for the whole branch tree. POST /admin/reindex (:864) and GET /skills/install.sh (:788) call it as well.
4. **propagation** `src/github.js:117` (fetchRepoTar): The tarball response body is piped through DecompressionStream('gzip') with no byte counter or cap.
5. **sink** `src/github.js:118` (fetchRepoTar): new Response(gunzip).arrayBuffer() materialises the entire decompressed tar in isolate memory, including blobs that are never indexed. tarEntries (:123) then indexes into it.

**Evidence.**
- `src/github.js:118`: The decompressed output is buffered with arrayBuffer() and no cap. In the hunter's sandbox stub, a 49,093-byte gzip became a 50,334,208-byte buffer without being rejected. That run's process.memoryUsage().arrayBuffers deltas were noisy (+10.3, +53.9 and +31.9 MiB), so only the buffer byteLength is relied on here.
- `src/github.js:123`: tarEntries takes a complete ArrayBuffer and indexes into it with subarray, so the current design cannot stream or stop early.
- `src/index.js:483`: update_note commits caller content through putFile with no size bound. In the verify-02 sandbox harness, with stubbed fetch and D1, a dummy write key scoped to project:alpha got ok/created for two 8 MiB vault/projects/alpha/blobN.bin files. Each became an ~11.2 MB Contents PUT. The only D1 writes were api_keys last_used updates, so the files were not indexed. As a control, a write to vault/topics/x.md with the same key was refused (forbidden).
- `src/index.js:29`: fullReindex walks tarEntries only after fetchRepoTar has buffered the whole tree. The DELETE batch at :32 runs after parsing, so a memory failure leaves the index stale rather than wiped. In the harness, the cron path buffered a 16,781,312-byte tar from a 16,578-byte gzip. 16,777,216 of those bytes were written by the project:alpha key.
- `src/index.js:791`: GET /skills/install.sh (:784-788) is reachable by any authenticated principal and calls fetchRepoTar/tarEntries over the whole tree before any per-skill scope filtering. In the harness it buffered the same 16,781,312-byte tar, so growth in one project prefix hits every key holder's installer.
- `src/index.js:899`: The cron work() runs fullReindex first and has no try/catch around it. A throw or isolate failure there also skips the hygiene snapshot (:901-903) and recordRollup (:907) in the same invocation.

**Blockers.**
- The isolate memory limit for this Workers account and plan (documented publicly as 128 MB) is not in the source. Also unobserved locally: whether arrayBuffer() concatenation peaks near 2x the decompressed size in workerd, and so whether a given tree size actually exceeds the limit or is not reachable. The local container is capped at 256 MiB and was deliberately not driven to OOM.
- Also not source-visible: the largest file GitHub accepts through the Contents API PUT or a Git Data tree with inline content, the Workers request-body limit for /mcp on this plan, and update_note's own per-request memory. The harness showed 8 MiB of content becoming an ~11.2 MB outbound body plus base64 intermediates. Together these decide whether a scoped writer can reach the threshold, and in how many calls.
- Whether GitHub's tarball endpoint (redirecting to codeload) caps, times out or refuses very large trees, and whether Workers CPU or wall-time limits fail first, is outside the repository.

**Local plan.** In the approved sandbox, rerun agents/verify-02/artifacts/tarball-scope.mjs. It uses a dummy project:alpha write key with stubbed D1 and GitHub. Confirm that update_note accepts in-scope non-.md blobs without a size check, refuses out-of-scope paths, and that cron fullReindex and /skills/install.sh both buffer a tar whose size equals the full tree including the writer's blobs. Then add a TransformStream byte counter between DecompressionStream and the tar reader, plus a content-length cap in update_note, save_session and save. Assert that each rejects cleanly past a configured limit (for example 32 MiB tree, 1 MiB file) and that the scoped writer's oversized write is refused.

**Owner-observed check.** Owner-observed, on a staging Worker bound to a throwaway test repo, never production. Using a write key scoped to project:test, commit a few large non-.md files under vault/projects/test/ through update_note, recording the per-call size at which GitHub or Workers rejects the write. Continue until the branch tree is about 100-150 MB decompressed. Then call POST /admin/reindex and GET /skills/install.sh once each with a separate key. Check the Worker logs and tail for 'Exceeded Memory Limit', CPU, or other limit errors, and check whether GitHub's tarball endpoint served the tree at all. Delete the files from the branch head afterwards and confirm both endpoints recover.

## 3. Read-only scoped keys can spend the owner's single shared GitHub API budget, and one JSON-RPC batch turns into N GitHub calls, which can block the owner's writes and indexing

`src/github.js:shared-GITHUB_TOKEN-no-per-principal-accounting`

Every GitHub call the Worker makes is authorised with one shared PAT, env.GITHUB_TOKEN (src/github.js:7). No code counts or limits GitHub usage per principal. A read-only managed key scoped to a single folder can send one POST /mcp JSON-RPC batch of any length (src/index.js:884). Each tools/call read_note for a path that is inside its scope but not in the D1 index falls through to getFile (src/index.js:417), which makes one GitHub Contents API request. Nothing caches the miss, so N messages produce N GitHub calls. These other paths also reach GitHub: get_context and list_skills go through readSkillsConfig while vault/skills.md is not indexed (src/skills.js:122); every GET /skills/install.sh fetches a full repo tarball with no cache (src/index.js:788); and a scoped write key's update_note makes a GET and a PUT. Once the PAT's GitHub rate limit runs out, every GitHub-backed operation fails for every principal until GitHub resets the limit. That includes the owner's root update_note and save, webhook indexing and the nightly fullReindex. The verifier reproduced this independently in the sandbox. An out-of-scope read_note made 0 GitHub calls, because the scope check holds. A read key's batch of 1 made 1 call and a batch of 25 made 25 calls, all with the same shared Bearer token. With a stub budget of 30 calls, a reader batch of 30 used it all, and the owner's root update_note then returned isError=true with 'GitHub GET ... -> 403: {"message":"API rate limit ...'. Recovery is limited to GitHub's reset window, and the owner can revoke the key. The real-world bar for exhaustion depends on the PAT's actual limit and the Workers per-invocation subrequest cap. Both are deployment and provider facts.

**Claimed root cause.** All principals share one upstream quota (GITHUB_TOKEN) and nothing accounts for it per principal. The /mcp handler runs every message in a JSON-RPC batch with no length cap (src/index.js:884-888). read_note falls back to GitHub on any D1 miss for an in-scope path and does not cache the miss (src/index.js:417). The only fan-out cap in the source is the webhook's 40-path slice. The /mcp, /skills/install.sh and readSkillsConfig paths have no equivalent cap, wrangler.jsonc declares no rate-limit binding, and resolvePrincipal/allowed/canWrite (src/auth.js) keep no usage counters.

**Trace.**
1. **entrypoint** `src/index.js:884` (fetch POST /mcp): An authenticated principal, here a read-only managed key, posts a JSON array, which becomes msgs with no cap on length.
2. **propagation** `src/index.js:887` (fetch POST /mcp): handleRpc runs once per message, in order, for the same principal. Errors from each tools/call are caught (index.js:614-619), so a failure does not stop the batch.
3. **propagation** `src/index.js:413` (callTool read_note): allowed() is a startsWith prefix check, so any path under the key's prefix passes, including paths that do not exist. An out-of-scope path is denied with 0 GitHub calls.
4. **propagation** `src/index.js:417` (callTool read_note): When D1 has no row for the path, getFile runs on every call. Nothing caches the miss.
5. **propagation** `src/github.js:25` (getFile): A Contents API GET goes through gh() to api.github.com.
6. **sink** `src/github.js:7` (headers): Every request carries the single shared Bearer env.GITHUB_TOKEN, so the read key's calls use up the owner's GitHub rate-limit budget.

**Evidence.**
- `src/index.js:884`: const msgs = Array.isArray(body) ? body : [body]; has no cap on msgs.length. The verifier saw a batch of 25 produce exactly 25 GitHub GETs.
- `src/index.js:417`: read_note calls getFile on every D1 miss, with no negative cache and no per-key counter.
- `src/skills.js:122`: readSkillsConfig falls back to getFile when vault/skills.md is not indexed. get_context reaches it through skillsPayload and list_skills reaches it at index.js:574.
- `src/index.js:788`: Every GET /skills/install.sh from any authenticated principal calls fetchRepoTar, a full tarball download with no cache.
- `src/index.js:482`: update_note makes a getFile GET and then a putFile PUT, so a scoped write key costs 2 calls per message and also reaches GitHub's content-creation secondary limits.
- `src/github.js:7`: The Authorization header comes from the single env.GITHUB_TOKEN for every principal.
- `wrangler.jsonc:1`: The config has no rate-limit binding and declares no limits. The only fan-out cap in the source is the webhook's slice(0, 40) at src/index.js:772.

**Blockers.**
- The deployed PAT's actual GitHub primary rate limit (x-ratelimit-limit, normally 5000/h for a user PAT) is a provider/account fact not in the repository, as is whether the token owner's other tooling shares that budget.
- The Workers per-invocation subrequest limit on the deployed plan caps GitHub calls per HTTP request (an uncaught fetch failure inside the batch becomes a per-message error). It decides how many HTTP requests a read key needs to exhaust the budget, which is a deployment fact.
- GitHub secondary rate limits (concurrency and per-minute point costs, with higher costs for content-creating PUTs) may trigger before the primary limit. These are provider facts that decide the write-key variant and how long blocking lasts.

**Local plan.** Re-run agents/verify-08/artifacts/quota_verify.mjs in the sbx sandbox (GitHub stubbed in memory, dummy keys, node:sqlite D1). Expected output: an out-of-scope read_note makes 0 GitHub calls; a read-only key scoped to vault/projects/demo/ sending batch N=1 makes 1 call and N=25 makes 25, all with 'Bearer ghp_dummy_shared'; with a modelled budget of 30, a reader batch of 30 uses it up and the owner's root update_note returns isError=true with 'GitHub GET ... -> 403'. agents/hunter2-quota/artifacts/github_quota.mjs also covers the get_context/list_skills, install.sh and update_note variants.

**Owner-observed check.** Do not run any batch against production. The owner runs `gh api rate_limit` with the deployed PAT to read resources.core.limit and current usage, and checks whether other tooling uses the same token. The owner reads the Workers plan's subrequest limit per invocation (dashboard or plan docs) and calculates ceil(core.limit / subrequest_limit), the number of POST /mcp batches a read key needs to exhaust the hourly budget. The owner also checks GitHub's published secondary rate-limit rules for REST content writes, to size the write-key variant, and confirms in api_keys.last_used whether usage per key is visible for revocation.

## 4. Telemetry hook spools tool-call records into a shared /tmp/brain-spool with no ownership, mode or symlink checks

`src/hook.js:hook-runtime:shared-tmp-spool-dir`

The PostToolUse hook that GET /hooks/install.sh ships sets its spool to ${BRAIN_SPOOL:-${TMPDIR:-/tmp}/brain-spool} and creates it with a plain `mkdir -p`. It sets no umask, runs no chmod and checks no owner. When TMPDIR is unset in the hook environment, which is common on Linux servers and VPSes, every local user shares that path. Each record holds the first 500 characters of every Bash command, scrubbed only by a regex blocklist, plus Edit/Write/Read file paths, WebFetch URLs and queries, short MCP arguments, cwd and the project slug. Records are appended with Python open(path, 'a'), which takes the default umask (usually 0644 files in a 0755 directory) and follows symlinks. Even when the victim creates the directory first, any other local user can read the victim's <sid>.jsonl and .batch files. If another user creates /tmp/brain-spool first (for example mode 0777 with no sticky bit), that user owns it. They can then delete or rename the victim's spool files, and they can replace <sid>.jsonl with a symlink to a file the victim can write, so the victim's next append writes a JSON line into that file. Linux fs.protected_symlinks only covers sticky world-writable directories, so it does not apply here. They can also plant *.batch files that the victim's detached flush reads and POSTs to /ingest/tool-calls with Authorization: Bearer <victim key>, and those records land in the victim's D1 tool_calls telemetry. The credentials file stays under ~/.config with umask 077, so the key itself is not exposed. The impact is disclosure of command and path telemetry, integrity loss of telemetry, and appends of victim-content JSON lines into a victim-writable file the attacker picks.

**Claimed root cause.** src/hook.js:31-32 picks a predictable shared default path under /tmp and creates it with `mkdir -p` with no `-m 700`, no umask and no check of owner or mode. src/hook.js:170 opens <spool>/<sid>.jsonl for append with no O_NOFOLLOW, no O_EXCL and no restrictive mode. src/hook.js:201-213 rotates and reads every *.jsonl and *.batch in the directory, whoever created it. src/hook.js:229-235 POSTs the contents with the user's key. The installer's `umask 077` (hook.js:284) only covers the credentials file, not the spool.

**Trace.**
1. **entrypoint** `src/hook.js:31` (hookScript): On every PostToolUse invocation the hook sets SPOOL to ${BRAIN_SPOOL:-${TMPDIR:-/tmp}/brain-spool}. That is a fixed, predictable shared path whenever TMPDIR is unset.
2. **propagation** `src/hook.js:32` (hookScript): mkdir -p "$SPOOL" succeeds whether or not the directory already exists and whoever owns it. No chmod 700, umask or owner check follows (confirmed in the decoded shipped script).
3. **propagation** `src/hook.js:170` (PY_APPEND): open(path, 'a') on <spool>/<sid>.jsonl follows a pre-placed symlink and creates the file with the default umask (typically 0644). The record holds the Bash command, file paths, URLs, cwd and MCP args.
4. **sink** `src/hook.js:207` (PY_FLUSH): Every *.batch file in the spool, including any another user planted, is read as JSON lines (line 213) and POSTed to /ingest/tool-calls with Authorization: Bearer <user key> (lines 229-235).

**Evidence.**
- `src/hook.js:31`: The decoded hook script that hookInstaller() emits contains SPOOL="${BRAIN_SPOOL:-${TMPDIR:-/tmp}/brain-spool}" (verify-09 sandbox run of agents/verify-09/artifacts/spool-check.mjs).
- `src/hook.js:32`: The decoded script has `mkdir -p "$SPOOL" 2>/dev/null || exit 0`. A search of the whole decoded hook script for umask, chmod, os.chmod, O_NOFOLLOW, st_uid, getuid, 0o700 and `-m 7` found nothing.
- `src/hook.js:139`: summary['command'] keeps the first 500 characters of every Bash command, scrubbed only by the regex PATTERNS at lines 64-76. Paths (141), URLs and queries (143-144) and short MCP args (149-150) are kept as well.
- `src/hook.js:170`: `with open(path, "a", encoding="utf-8")` has no mode, no O_NOFOLLOW and no O_EXCL.
- `src/hook.js:203`: PY_FLUSH renames every *.jsonl in the directory to .batch. Lines 207-213 then read every *.batch, whoever created it.

## 7. The telemetry rollup drains the whole buffer in one pass, with work set by the caller's session and day count, makes no progress after a partial failure, and re-appends rows it already wrote

`src/index.js:rollUpToolCalls:unbounded-single-pass-nonidempotent-drain`

A write-role key, including one scoped to a single project, can POST /ingest/tool-calls with up to 500 records per request. Each record's ts and session are chosen by the caller, and the server applies no aggregate cap. A past-dated ts (any YYYY-MM-DD before today, e.g. 1970-01-01) makes the row eligible for the next drain. sessionKey() and the ts prefix set the group key, so each record can be its own (day, session) group. rollUpToolCalls loads every eligible row with .all() and no LIMIT. For each group it does one R2 get and one R2 put, so the number of binding calls is 2 x groups, all in one invocation. The DELETE runs only after every put succeeds, and no per-group checkpoint exists. If an invocation hits a per-invocation ceiling partway (subrequests, memory, CPU or D1 result size), nothing is deleted. The next run starts again from the first group and appends the same lines to objects it already wrote. A backlog larger than the deployed ceiling therefore fails every night, makes no progress, and adds one more duplicate copy to the leading groups each time. The failure is also silent. When rollUpToolCalls throws, recordRollup never writes meta.last_rollup, so /health keeps showing the last successful drain. The cron path only console.logs the error. On the cron path, fullReindex runs first in the same invocation and uses up part of the same budget. Verified locally with a simulated ceiling of 30 binding calls over 40 attacker-made groups. Both capped runs returned 500 and all 40 rows stayed buffered. last_rollup kept the earlier success stamp. After the final uncapped run, 15 R2 objects held the same record 3 times. Impact is limited to the operator's telemetry (an R2 archive that is never drained or is duplicated, plus a D1 buffer that keeps growing in the D1 database that also holds notes, keys and OAuth). Notes, auth and git are not affected.

**Claimed root cause.** rollUpToolCalls (src/index.js:672-699) runs an unbounded SELECT (line 675-678) and fans out an R2 read-modify-write for every (day, session) group in one invocation (lines 688-696). The single DELETE is placed after all writes (line 697), with no per-group delete or checkpoint, so a partial failure discards all progress. The get+put append at lines 691-693 is not idempotent, so replaying a group duplicates its lines. ingestToolCalls (lines 646-667) lets the caller choose the day (line 650) and session (via sessionKey, line 49) with no aggregate bound, so a write key decides the group count. recordRollup (lines 702-707) stamps meta only on success, which hides repeated failures from /health.

**Trace.**
1. **entrypoint** `src/index.js:822` (fetch POST /ingest/tool-calls): Any write-role principal (canWrite, prefix-agnostic) submits up to INGEST_BATCH_CAP=500 records per request, each with a caller-chosen ts and session.
2. **propagation** `src/index.js:650` (ingestToolCalls): day is taken from the caller's ts prefix. Any past date makes the row eligible for the next drain, and distinct sessions/days create distinct groups.
3. **propagation** `src/index.js:907` (scheduled): The nightly cron calls recordRollup after fullReindex in the same invocation. POST /admin/rollup at line 840 calls it too.
4. **propagation** `src/index.js:675` (rollUpToolCalls): All rows with day < today are loaded with .all() and no LIMIT.
5. **propagation** `src/index.js:691` (rollUpToolCalls): One LOGS.get and one LOGS.put (line 693) per distinct day/session group, all in one invocation.
6. **sink** `src/index.js:697` (rollUpToolCalls): The DELETE runs only after every group has succeeded. On a mid-loop throw, all rows stay buffered and the next run re-appends the groups it already wrote.

**Evidence.**

- `src/index.js:693`: LOGS.put(key, head + lines) rewrites the object with the previous content plus the new lines, so replaying a group duplicates it.

## 9. Quadratic wikilink regex lets one note from a scoped writer stall full reindex and webhook indexing

`src/parse.js:extractLinks:quadratic-unclosed-wikilink-regex`

extractLinks (src/parse.js:44) runs a global backtracking regex. Its target group `[^\]|#\n]+` admits '[', and its heading group `#[^\]|\n]*` and alias group `\|[^\]\n]*` admit '[' as well. Every '[[' on one long line starts a match attempt that scans to the end of the line, fails to find ']]', and backtracks. Work is O(L^2) per line, and no note-size, line-length, or link-count cap runs before parsing. In the audit sandbox (Node 26, 1 CPU), the retained verify-19 transcripts show extractLinks on a single line of '[' taking 3.6-5.6 ms at 2 KB, 13.5-25.9 ms at 4 KB, 51-81 ms at 8 KB, 204-227 ms at 16 KB and 784 ms at 32 KB, about 3.5-4x per doubling. parseNote on the same body with frontmatter took 3.5, 13.2, 49.7, 193 and 778 ms from 2 KB to 32 KB, 3.75-4.0x per doubling. Two controls stayed near-linear: a benign '[[a]]' body took 0.23 ms at 32 KB, and the same '[' bytes split into 200-character lines took 6.2 ms. Extrapolating the quadratic gives about 3 s at 64 KiB, about 50 s at 256 KiB and about 13 min at 1 MiB. All of these sizes are under the 2 MB D1 row limit. Any managed key with write role can commit such a note inside its own prefix through update_note, save_session or save, as can anyone with push access to the repo. putFile commits to git before upsertLocal parses, so the note persists even if that request is killed. Three paths then re-parse it with no per-note budget: fullReindex parses every tar entry in one invocation before its DELETE batch (nightly cron and /admin/reindex), the webhook handler re-parses changed paths in waitUntil, and upsertLocal re-parses on every app or MCP write. Killing fullReindex leaves the D1 index stale but intact, because the parse loop runs before the deletes. It also skips the cron's hygiene snapshot and telemetry rollup. Other notes in the same webhook batch go unindexed. Damage is to the shared index (search, graph, backlinks, hygiene for every principal) and to the operator's Worker CPU spend. It lasts until the owner deletes the note. Whether this crosses the kill threshold depends on the deployed CPU limit, which wrangler.jsonc does not set.

**Claimed root cause.** All three character classes in /\[\[([^\]|#\n]+)(?:#[^\]|\n]*)?(?:\|[^\]\n]*)?\]\]/g accept '[', so each '[[' start position on a line rescans to the end of that line. Nothing caps body size, line length or match count before extractLinks runs from parseNote (src/parse.js:104). Changing only the first group is not enough: the same sandbox showed the hunter's group-1-only fix staying quadratic on '[[a#' and '[[a|' repeated (38-56 ms at 16 KB, about 4x per doubling). Excluding '[' from all three groups stayed flat (0.01-0.04 ms at 16 KB) and returned the same link set on a sample.

**Trace.**
1. **entrypoint** `src/index.js:479` (callTool update_note): A managed key with write role and a scoped prefix commits a note whose body contains one long line of '[' (or of '[[a#' / '[[a|' repeated). canWrite and allowed are the only gates, and neither checks content size.
2. **propagation** `src/indexer.js:48` (upsertLocal): The same request re-parses the content synchronously after putFile has already committed it to git.
3. **propagation** `src/index.js:30` (fullReindex): The nightly cron (src/index.js:899) and /admin/reindex call parseNote on every tar entry in one invocation, before the DELETE batch, with no per-note budget or skip.
4. **propagation** `src/index.js:20` (indexFromGitHub (webhook)): A push that touches the note re-parses it inside ctx.waitUntil.
5. **propagation** `src/parse.js:104` (parseNote): links: extractLinks(body), with no size guard.
6. **sink** `src/parse.js:44` (extractLinks): matchAll with a backtracking regex whose target, heading and alias groups all admit '[' costs O(L^2) CPU per line on an unclosed run.

**Evidence.**
- `src/parse.js:44`: The regex's three character classes ([^\]|#\n], [^\]|\n], [^\]\n]) all exclude ']' but not '['. Retained transcripts show 204-227 ms at 16 KB and 784 ms at 32 KB on a single '[' line, about 3.5-4x per doubling.
- `src/index.js:29`: The full-reindex parse loop parses every indexable tar entry, with no per-note budget, try/skip or size filter.
- `src/index.js:899`: The cron runs computeHygiene and recordRollup only after fullReindex returns, so one invocation killed for CPU loses all three.
- `src/index.js:483`: update_note calls putFile before upsertLocal, so the poison note is committed to git even if the parse in that same request is killed.
- `wrangler.jsonc:1`: There is no limits.cpu_ms block, so the account plan's default Worker CPU limit applies and is not visible in source.

**Blockers.**
- The deployed Workers CPU limit is not visible in source (wrangler.jsonc sets no limits.cpu_ms), for both the scheduled (cron) invocation and the fetch/waitUntil invocations. It sets the note size at which fullReindex and webhook indexing get killed. The quadratic cost and the missing bound are confirmed locally. The shared-availability impact (a stale index every night, skipped hygiene and rollup) has not been observed on the deployed Worker and must not be tested against production.

**Local plan.** In the audit sandbox, run agents/verify-19/artifacts/wikilink-growth.mjs, which imports /target/src/parse.js. It reproduces the quadratic curve for extractLinks and parseNote at 2-32 KB, runs the benign and newline-split controls, and checks a full fix on 1,000,000 '['. Then run agents/verify-19/artifacts/wikilink-fix-check.mjs. It shows that changing only the target group leaves the '[[a#' and '[[a|' variants quadratic, while excluding '[' from all three groups stays linear and returns the same links. Source fix: in src/parse.js:44 use /\[\[([^\][|#\n]+)(?:#[^\][|\n]*)?(?:\|[^\][\n]*)?\]\]/g. Optionally also cap line length or body size before matching. Add a regression check that extractLinks runs in under 50 ms on '['.repeat(1e6), '[[a#'.repeat(25e4) and '[[a|'.repeat(25e4).

**Owner-observed check.** Owner-observed and read-only. In the Cloudflare dashboard, check the account plan and any CPU limit configured for the brain-mcp Worker, for both scheduled and fetch invocations. Check Workers Logs/observability for 'exceeded CPU' or 'nightly reindex failed' on the 03:00 UTC cron, and compare meta.last_full_reindex with the cron schedule. Do not commit a test note to the production repo and do not call /admin/reindex to test this.

## 10. Graph hover tooltip renders note frontmatter title/type as HTML, letting a path-scoped write key run script in the owner's admin web session

`ui/src/views/GraphView.tsx:nodeLabel:frontmatter-title-html`

A principal that can get a note indexed controls that note's frontmatter title and type. A write key scoped only to vault/topics/ can set them with update_note. A write key scoped only to vault/logs/ can set them with append_session_log, because the raw surface argument is interpolated into YAML: a newline in surface injects new title:/type: keys, and the later duplicate type: key overrides type: session. parseNote copies both values verbatim, upsertNotes stores them in D1, and GET /app/api/graph returns them unescaped to every session whose scope covers the note. For an admin or root session that is every note. GraphView builds the force-graph nodeLabel as the string `${n.title || n.id}  ·  ${n.type}`. In the lockfile-pinned versions (force-graph 1.51.4, float-tooltip 1.7.5, d3-selection 3.0.0), hovering a node passes the label accessor result to tooltip.content(). For string content, float-tooltip calls tooltipEl.html(), and d3-selection html() assigns innerHTML. When the owner opens the Graph tab and hovers the node, a payload such as <img src=x onerror=...> would run on the brain origin. Same-origin fetches from that script carry the HttpOnly SameSite=Lax brain_session cookie. POST /app/api/keys accepts that cookie with no CSRF token or re-authentication and returns a plaintext admin key with whole-brain scope. The scoped writer's own key gets 403 on that endpoint.
