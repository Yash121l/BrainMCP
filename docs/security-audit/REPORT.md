## 2. Security posture

The single-owner case is in decent shape. Credentials are 192-bit random values stored as SHA-256 hashes, the webhook HMAC fails closed, D1 queries are parameterised, CORS is closed, the session cookie is HttpOnly and SameSite=Lax, and no secrets are in the repository or its history.

The problems start as soon as the owner hands out a scoped key, which is the product's main sharing model. The scope check in `allowed()` is a raw `startsWith` on an uncanonicalised path, while GitHub receives a dot-normalised URL. Any scoped key can therefore read any file in the private repo, and a scoped write key can overwrite binding rules and skill files (high). The skills installer then turns repo file names into shell, so a skill-scoped writer can run commands on every machine that installs skills (high). Around those two sit a cluster of lifecycle gaps. Revocation, narrowing and expiry don't reach credentials derived from a key. OAuth codes go to any redirect URI. A scoped admin is treated as a whole-brain admin. Together these mean "revoke the key" and "this key only sees project X" don't hold today.

Fix the path canonicalisation and the installer quoting first. Then bind derived credentials to their parent key on every lookup, and enforce client registration in `POST /authorize`. Most of the needs-validation leads (D1 and CPU limits, Preview URLs, the graph tooltip) need the owner to look at the Cloudflare dashboard or run a browser test against a throwaway deployment.

## 4. Confirmed finding details

### 1. '..' segments in MCP path arguments bypass key scopes: any scoped key can read any repo file, and a scoped write key can overwrite any file, including skills that /skills/install.sh ships to client machines

- **Severity:** high (likelihood high, impact high; confidence high)
- **Fingerprint:** `brainmcp:auth.allowed:unnormalized-path-prefix-scope-bypass`
- **Source:** `src/index.js:871` → `src/index.js:615` → `src/auth.js:94` → `src/index.js:413` → `src/auth.js:112` → `src/index.js:417` → `src/github.js:25` → `src/index.js:481` → `src/github.js:41` → `src/index.js:811`
- **Lower-trust principal:** The attacker holds any managed key with a non-empty scope list, or an OAuth or web-session token derived from one. Scoped keys are the lower-trust credential the operator hands to other people, machines and AI clients. Read role is enough for the out-of-scope read through read_note. Write or admin role is needed for out-of-scope writes through update_note. No skills/ scope is needed to write under skills/.

allowed() authorizes a path with a plain String.startsWith check against the key's expanded prefixes. It never canonicalizes the path. read_note and update_note then pass the same raw string to getFile and putFile. Those functions put it into a GitHub Contents API URL with encodeURIComponent(path).replace(/%2F/g,'/'), which leaves '.' and '..' segments literal. The WHATWG URL parse that fetch performs removes the dot segments, so GitHub receives a different, out-of-scope path from the one that was authorized. Read role is enough to read any file in the private brain repo through the read_note GitHub fallback, which runs whenever D1 misses, and D1 always misses for a '..' path. Write role is enough to create or overwrite any file the Worker's GITHUB_TOKEN can write: other projects' notes, vault/rules/<slug>.md (binding rules that get_context serves to agents), and skills/**. /skills/install.sh rebuilds its payload from repo HEAD for every installing principal (root and admin get everything) and adds chmod +x for *.sh files. A lower-trust write key can therefore replace an owner-authored skill or plant an executable helper, and that file lands in ~/.claude/skills on the owner's and other key holders' machines. project:<slug> keys are affected too: expandScopes adds exact note paths (for example vault/projects/alpha.md) and the folder vault/projects/alpha/, and startsWith treats both as raw prefixes, so 'vault/projects/alpha.md/../x' passes. Sibling sinks with the same root cause, not separately demonstrated here: save and save_session send '..' tree paths to the Git Data API through multiCommit. Whether GitHub rejects or normalizes those is not established. get_skill and /app/api/note also accept '..' paths, but they only do exact-path D1 lookups, so they give no out-of-scope reach.

**Root cause.** allowed() (src/auth.js:109-113) compares the uncanonicalized caller path with raw startsWith and no segment boundary. getFile and putFile (src/github.js:25,41) build request URLs whose dot segments the fetch URL parser resolves. The authorized string and the fetched or written resource therefore differ.

**Bounded local reproduction.** Holder of a dummy managed key scoped to ['vault/logs/'] (read role for reads, write role for writes), or to ['project:alpha'], calling MCP tools/call on POST /mcp.

1. Run agents/verify-01/artifacts/verify-dotseg.mjs in the no-network sandbox. It imports the real Worker default export from /target/src/index.js with a fake env.DB. The fake resolves three dummy keys: read role ['vault/logs/'], write role ['vault/logs/'], and read role ['project:alpha']. Its notes table holds only vault/projects/alpha.md under project alpha, and every exact-path notes lookup misses.
2. Global fetch is stubbed with an in-memory GitHub Contents/tarball fake. The stub builds new Request(input) (the URL parse real fetch performs) and records both the raw URL the code built and the path actually sent.
3. Each payload is POSTed to /mcp with Authorization: Bearer <dummy key>, alongside controls: the direct out-of-scope path for each key, and the dot-segment write with the read-role key. GET /skills/install.sh is then called with the dummy root token, and the generated script is printed, never executed.

**Conditions.** authentication level: The attacker holds any managed key with a non-empty scope list, or an OAuth or web-session token derived from one. Scoped keys are the lower-trust credential the operator hands to other people, machines and AI clients. authorization role: Read role is enough for the out-of-scope read through read_note. Write or admin role is needed for out-of-scope writes through update_note. No skills/ scope is needed to write under skills/. user interaction: For impact on a client machine, the owner or another key holder whose scope covers skills/ later runs /skills/install.sh | sh, and then an agent loads the replaced skill or the planted helper is invoked. environmental dependency: The Workers fetch URL parser resolves '.' and '..' path segments, as the WHATWG URL standard requires (the default at the configured compatibility date). In Node 26 in the harness, new Request()/new URL() did resolve them. third party dependency: Write reach is bounded by what the Worker's GITHUB_TOKEN can write. For example, .github/workflows/* would also need workflow permission.

**Observed result.** Controls: read_note 'vault/projects/beta-secret.md' returned 'forbidden: no access' for both the vault/logs/ key and the project:alpha key, update_note 'vault/rules/beta.md' and 'skills/evil/run.sh' returned 'forbidden: no write access', and a read-role key's dot-segment update_note returned 'key is read-only'. Bypass: the read-role vault/logs/ key's read of 'vault/logs/../projects/beta-secret.md' returned 'V01-DUMMY-BETA-SECRET' with source 'github (not yet indexed)'. The wire showed raw '/contents/vault/logs/../projects/beta-secret.md?ref=main' and sent '/contents/vault/projects/beta-secret.md?ref=main'. The project:alpha key read the same secret through 'vault/projects/alpha.md/../beta-secret.md'. With the write-role vault/logs/ key: update_note 'vault/logs/../rules/beta.md' returned ok, created:false, sent GET and PUT /contents/vault/rules/beta.md, and the fake repo file became 'V01-DUMMY-INJECTED-RULES'. update_note 'vault/logs/../../skills/evil/run.sh' created skills/evil/run.sh, and 'vault/logs/../../skills/trusted/SKILL.md' replaced the existing skill (created:false). install.sh returned 200, contained the base64 of both attacker bodies, and included 'chmod +x "$SKILLS_DEST/evil/run.sh"'.

**Impact and priority.** The key-scope boundary is gone for the GitHub-backed tools. Any scoped holder can read any file in the private brain repo. A scoped write key can overwrite other projects' notes and binding agent rules, and can plant or replace skill files that the installer ships with chmod +x to the owner's and other key holders' machines. Locally this was observed as file overwrites and as the attacker content inside the generated installer, not as code execution. Scoped keys are the product's normal way to grant access to other people, machines and AI clients. The bypass is one tools/call with a literal '..' path, and read role is enough for reads. Client-machine impact from planted skills also needs a later install.sh run by a broader principal.

**Smallest fix.** Use one shared canonical-path validator. Reject empty, '.' and '..' segments, a leading '/', backslashes and control characters. Call it inside allowed() so every caller fails closed, and make allowed() match file prefixes exactly and directory prefixes on a '/' boundary. As defense in depth, call the same validator in every github.js path sink (getFile, putFile and multiCommit tree paths), so the authorized string is exactly the one sent to GitHub. Optionally require an explicit skills/ write scope, or admin, for writes under skills/. Regression cases: read_note, update_note, save topics and save_session with 'vault/logs/../x.md', 'vault/projects/alpha.md/../x.md', 'vault/projects/alpha/../x.md' and 'vault/logs/./x.md' must return forbidden for scoped keys, while canonical in-scope paths keep working.

### 2. Skill file names from a scoped write key execute as shell on every machine that runs /skills/install.sh

- **Severity:** high (likelihood medium, impact high; confidence medium)
- **Fingerprint:** `src/index.js:skills-install.sh:unquoted-repo-path-shell-injection`
- **Source:** `src/index.js:479` → `src/index.js:481` → `src/github.js:41` → `src/github.js:148` → `src/index.js:794` → `src/index.js:809`
- **Lower-trust principal:** The attacker holds a write- or admin-role managed key (or an OAuth token derived from one) whose scope includes some skills/ prefix (e.g. a delegated skill-author key). The KeysView UI supports path scopes, so such a key is a normal thing to issue.

GET /skills/install.sh builds a POSIX shell script and interpolates each repo-relative path under skills/ into double-quoted shell: `mkdir -p "$SKILLS_DEST/<dir>"` (index.js:809), `base64 $B64D > "$SKILLS_DEST/<rel>"` (index.js:810), `chmod +x "$SKILLS_DEST/<rel>"` (index.js:811) and `echo "Done: <skill dir names>"` (index.js:813). Inside double quotes $(...), backticks and $VAR still expand and a literal double-quote ends the quoting. A holder of a write-role key scoped to any skills/ prefix can create such a file name via update_note (index.js:479) or save_session (index.js:488), because allowed() is a bare startsWith with no character restriction (auth.js:112). The file is committed to the git repo by putFile before any indexing step, so it persists regardless of D1 state. The next time the owner (or any principal whose key can read that path) runs the documented `curl ... /skills/install.sh | sh`, the embedded command runs as that user at install time, before any skill is reviewed or invoked.

**Root cause.** src/index.js:808-813 inserts f.rel, dir and the skill directory names into double-quoted shell with no escaping and no safe-character allowlist; only the file body is protected (quoted base64 heredoc). Write tools accept any path that passes the prefix-only allowed() check (auth.js:112), so path characters are never restricted before they reach the installer generator.

**Bounded local reproduction.** Holder of a write key scoped to skills/team-skill/ seeking command execution on the owner's machine beyond their authority to edit skill text.

1. Harness agents/verify-16c/artifacts/v16c-install-name-injection.mjs: import /target/src/index.js default worker with a stubbed env (in-memory DB resolving bk_scopedwritekey -> role write, prefixes ['skills/team-skill/']; BRAIN_TOKEN root; LOGS stub) and a fetch stub that stores Contents API PUTs into an in-memory repo and serves them back as a gzip tarball.
2. POST the update_note JSON-RPC call to /mcp with the scoped key; the path is accepted and committed to the in-memory repo by putFile (the subsequent D1 indexing step is unrelated to the committed file).
3. GET /skills/install.sh with the root token and write the response to /work/run/install.sh.
4. Run /bin/sh /work/run/install.sh with cwd /work/run and SKILLS_DEST=/work/run/skills inside the no-network sbx container, then check for /work/run/INJECTED_marker.
5. Execute via: python3 tools/sbx.py run /Users/admin/security-audit-skill/BrainMCP/run-1 verify-16c v16c-install-name-injection.mjs --timeout 90

**Conditions.** authorization role: The attacker holds a write- or admin-role managed key (or an OAuth token derived from one) whose scope includes some skills/ prefix (e.g. a delegated skill-author key). The KeysView UI supports path scopes, so such a key is a normal thing to issue. user interaction: A victim whose key can read that path (typically the owner's root/admin key, which has empty prefixes and thus reads everything) runs the documented `curl -H 'Authorization: Bearer $KEY' .../skills/install.sh | sh`. third party dependency: GitHub's Contents/Git Data API accepts file names containing $, ( ), and spaces; git permits any byte except NUL and '/'. The local reproduction used a fetch stub for GitHub, so this one acceptance fact is the only step not exercised against the real service.

**Observed result.** The scoped write key's path 'skills/team-skill/$(touch /work/run/INJECTED_marker)/notes.md' was accepted by allowed() and committed to the repo (repo keys listed it). The root-token /skills/install.sh returned status 200 and contained `mkdir -p "$SKILLS_DEST/team-skill/$(touch /work/run/INJECTED_marker)"` and the matching base64 redirect line. Running the script with /bin/sh printed 'Installing 1 skills (2 files)' and 'Done: team-skill'; marker before: false, marker after: true — the command embedded in the file name executed at install time. (update_note's JSON reply surfaced a D1-stub error from the indexing step after the commit; in production with a real D1 it returns ok:true, but the committed file and the resulting code execution do not depend on that step.)

**Impact and priority.** Arbitrary command execution as the installing user on the owner's or other key holders' machines, exposing local credentials including the root BRAIN_TOKEN and ~/.claude settings — well beyond the attacker's authority to edit skill text. Requires a write key scoped to skills/ to have been issued (the Keys UI supports path scopes) plus the owner or another reader re-running the documented installer. The malicious file is a single MCP call and persists in git once committed.

**Smallest fix.** Reject unsafe skill paths when generating the installer and emit every path as a single-quoted shell literal so no name can expand; optionally also reject such names in the write tools.

### 3. Scoped admin key can mint or self-grant whole-brain admin through /app/api/keys and can run global /admin routes, because isAdmin ignores scope

- **Severity:** medium (likelihood low, impact high; confidence medium)
- **Fingerprint:** `src/auth.js:isAdmin/scope-agnostic-key-management`
- **Source:** `src/app.js:295` → `src/auth.js:94` → `src/app.js:296` → `src/auth.js:115` → `src/auth.js:129` → `src/auth.js:169` → `src/index.js:836` → `src/index.js:838` → `src/index.js:697` → `src/index.js:860` → `src/index.js:862` → `src/index.js:32`
- **Lower-trust principal:** The attacker holds a managed key with role 'admin' and a non-empty scope (a path prefix or project:<slug>).

The operator can give out an admin key restricted to one project or folder. createKey accepts that combination, the key editor offers it (any role plus ScopePicker, with "Sees about N notes"), and allowed() enforces the scope on note reads. Every admin-gated route checks only isAdmin(p), which looks at role and nothing else. So the holder of an admin key scoped to vault/projects/alpha/ can: (1) POST /app/api/keys to mint a new admin key with prefixes [] (the whole brain), which is returned in plaintext; (2) PATCH /app/api/keys with its own id and prefixes [] to widen itself; (3) GET /app/api/keys and /app/api/scopes to list every key and every project slug, title and path, then edit or revoke other keys; (4) POST /admin/rollup to drain and delete every project's buffered tool_calls into R2; and (5) POST /admin/reindex to wipe and rebuild the whole notes/links/fts index. With the widened or minted key it can read every note and, because the role is admin and canWrite ignores scope, write any path in the git repo through the MCP write tools.

**Root cause.** isAdmin (src/auth.js:115) is `!!p && p.role === 'admin'` and never looks at p.scopes or p.prefixes. The /app/api/scopes and /app/api/keys handlers (src/app.js:247,292,296,306,317) and POST /admin/rollup and /admin/reindex (src/index.js:838,862) use it as their only authorization. createKey (src/auth.js:121-130) and updateKey (src/auth.js:140-177) accept any role and any normalized scope list, including [], with no check that it fits inside the caller's own role and scope and no bar on a key editing its own record. The global sinks fullReindex and rollUpToolCalls take no scope.

**Bounded local reproduction.** Holder of a managed admin key that the operator restricted to vault/projects/alpha/.

1. Run agents/verify-04/artifacts/verify04.mjs in the approved sandbox. It imports the real worker (default export of /target/src/index.js) with an in-memory fake D1 holding dummy notes vault/projects/alpha/a.md, vault/projects/beta.md (a project titled 'Beta Secret Project') and vault/secret/s.md, one dummy tool_calls row for project beta, an in-memory R2, and a stubbed fetch that serves a one-file dummy tarball and blocks all other network access.
2. As the operator, it calls createKey for an admin key and, as a control, a write key, both with prefixes ['vault/projects/alpha/'].
3. With the scoped admin key as the brain_session cookie, it requests the out-of-scope note, lists keys and scopes, POSTs a new admin key with prefixes [], reads the secret note with the minted key, PATCHes its own id to prefixes [], and reads the secret note again with the original key.
4. With a second scoped admin key as a bearer token, it POSTs /admin/rollup and /admin/reindex and checks D1 and R2 state before and after. The scoped write key is the negative control on both route families.

**Conditions.** authorization role: The attacker holds a managed key with role 'admin' and a non-empty scope (a path prefix or project:<slug>). data state: The operator has issued such a scoped admin key. createKey and the key editor both allow it. For the /admin variant, there are notes or buffered tool_calls outside the key's scope, which is the normal multi-project state.

**Observed result.** Sandbox exit 0, wall 0.16s. Scoped admin principal: role admin, prefixes ['vault/projects/alpha/']. Scope enforcement before escalation: out-of-scope note 403, /app/api/notes returns 1 note. GET /app/api/keys 200 (lists all keys); GET /app/api/scopes 200 (lists out-of-scope project ['beta','Beta Secret Project']). Control: the scoped write key gets 403 on POST /app/api/keys. Escalation: POST /app/api/keys with role admin and prefixes [] returns 201; the minted key reads vault/secret/s.md with 200 'secret dummy'. PATCH of its own id to prefixes [] returns 200 with []; the original key then reads vault/secret/s.md with 200 'secret dummy'. Control: the scoped write key gets 401 on /admin/rollup. The scoped admin's POST /admin/rollup returns 200 {rolled:1, objects:1}: the beta tool_calls buffer went from 1 row to 0 and was moved to R2 at tool-calls/2000-01-01/sess-beta.jsonl. The scoped admin's POST /admin/reindex returns 200 {indexed:1}: all three existing notes, including the out-of-scope ones, were deleted, and the index was rebuilt from the dummy tarball.

**Impact and priority.** A key meant for one project gets whole-brain read, write access to any path in the git repo through the MCP write tools, and control over every other key (list, mint, re-scope, revoke). It can also wipe and rebuild the shared index and drain all projects' telemetry buffer. The operator must first issue an admin key with a scope. Both the server and the UI support this, and the UI describes the key as bounded. But the admin role hint ('everything, including these keys') makes it less likely an operator would pick that combination and expect it to stay contained. Once such a key exists, exploiting it takes one authenticated request and no other conditions.

**Smallest fix.** Treat key management and the /admin routes as whole-brain authority. ### 10. A scoped write key can fill the shared D1 database with future-dated telemetry rows that the nightly rollup never drains

- **Severity:** low (likelihood medium, impact low; confidence high)
- **Fingerprint:** `src/index.js:ingestToolCalls:client-ts-day-unbounded-retention`
- **Source:** `src/index.js:822` → `src/index.js:825` → `src/index.js:647` → `src/index.js:650` → `src/index.js:676` → `src/index.js:697` → `schema.sql:73`
- **Lower-trust principal:** The caller holds a write-role managed key, or an OAuth or cookie token derived from one, with any path or project scope. Read-only keys are rejected.

POST /ingest/tool-calls accepts records from any write-role principal. The only checks are canWrite(p) and a cap of 500 records per request, and path or project scopes are never consulted. Nothing caps rows per key or in total, and no TTL applies. Each request with ~7.8 KB records adds about 3.9 MB of permanent payload to the D1 database that also holds the notes index, FTS, api_keys and OAuth tables. Anonymous /health shows the buffered count. The rows can only be removed by manual SQL.

**Root cause.** ingestToolCalls takes the retention key (day) from untrusted client input whenever it starts with a YYYY-MM-DD pattern (src/index.js:650). It bounds only each request's slice (src/index.js:647). rollUpToolCalls is the only drain, and both its SELECT and DELETE are limited to day < today (src/index.js:676, 697). So rows with a future or out-of-range day, which also sort after today, are kept forever. No aggregate, per-key or insert-time TTL bound exists for tool_calls.

**Bounded local reproduction.** Holder of a managed write key scoped to one project (prefixes ["project:demo"])

### 11. save(session_id) takes its commit path from session_key frontmatter that any write key can set, so another principal's session log can be redirected into the attacker's scope

- **Severity:** low (likelihood low, impact medium; confidence high)
- **Fingerprint:** `src/index.js:save:session-key-lookup-unbound-target-path`
- **Source:** `src/index.js:871` → `src/index.js:615` → `src/index.js:511` → `src/index.js:512` → `src/index.js:515` → `src/index.js:516` → `src/index.js:519` → `src/index.js:565` → `src/github.js:82`
- **Lower-trust principal:** The attacker holds a write-role managed key, or a token derived from one, whose scope includes a writable path for the plant. Here that is project:alpha, which grants vault/projects/alpha/.

For idempotent re-saves, the save MCP tool looks for an existing indexed note with type 'session' whose frontmatter session_key equals the caller's session_id. It then overwrites that note's path. The query searches every note in the vault, and both type and session_key are ordinary frontmatter that a write-role key can set on any note inside its scope. Take a write key scoped to project:alpha. If the owner's earlier session note is filed under alpha, project scope expansion makes it readable and writable to that key, and the key can read the owner's session id from the note's filename or frontmatter. The key then changes that note's session_key and plants a note under vault/projects/alpha/ with type: session and the owner's session_key. When the owner next calls save for the same session, even about project beta, which the key cannot read, the commit goes to the planted path. The re-index files it under project beta, but the path still matches the key's static vault/projects/alpha/ prefix, so the key reads the owner's beta summary and body back. Without the plant, the same re-save goes to vault/logs/sessions/ and the key cannot read it.

**Root cause.** src/index.js:512-515 sets sessPath from the first D1 row matching only type = 'session' AND json_extract(frontmatter,'$.session_key') = sessId, across the whole vault. Nothing requires the path to be that session's canonical vault/logs/sessions/<date>_<time>_<sessId>.md file, and nothing binds the row to the principal that created it. The allowed(p, sessPath) check at index.js:516 runs for the saving principal (root has no prefixes), so it does not catch a target chosen by a lower-trust writer.

**Bounded local reproduction.** Holder of a write key scoped to project:alpha, with no read access to project beta.

1. Run agents/verify-14/artifacts/save_redirect_verify.mjs in the parent sandbox (Node 26, no network). It imports /target/src/index.js with env.DB backed by node:sqlite loaded from schema.sql and global fetch replaced by an in-memory GitHub Contents/Git Data stub.
2. Each of the two scenarios seeds dummy vault/projects/alpha.md, vault/projects/beta.md and an owner session note filed under alpha with session_key vfySess7, plus a write api_keys row scoped ['project:alpha'].
3. Baseline: the owner saves (session_id vfySess7, project beta) with no attacker action. Attack: the attacker retags the owner note and plants the decoy, then the owner saves. All calls go through worker.fetch POST /mcp.
4. Compare the committed path and the attacker's read_note results. The script also evaluates the remediation queries against the final index.

**Conditions.** authorization role: The attacker holds a write-role managed key, or a token derived from one, whose scope includes a writable path for the plant. Here that is project:alpha, which grants vault/projects/alpha/. data state: The owner's earlier note for that session is filed under the attacker's project. This makes it readable, which leaks the session id, and writable, which allows the retag. Alternatively the attacker has a writable path that sorts before the owner's vault/logs/sessions/ note, or plants before the owner's first save with a known session id. With only a project scope and an out-of-scope owner note, vault/logs/ sorts before vault/projects/ and the plant loses. user interaction: After the plant, the owner calls save again with the same session_id. The tool contract tells agents to reuse it for idempotent re-saves. The later save covers a project the attacker cannot read.

**Observed result.** Baseline: the owner's save committed vault/logs/sessions/2026-09-29_090000_vfySess7.md, and the attacker's read of it was then 'forbidden'. Attack: save returned {"ok":true,"commit":"cX","files":["vault/projects/alpha/scratch.md"]}. The stub recorded a single commit to vault/projects/alpha/scratch.md. The attacker's read_note of that path returned project=[[projects/beta]] with DUMMY-BETA-SECRET-91 present, while read_note of vault/projects/beta.md stayed 'forbidden: no access to vault/projects/beta.md'. A filename-suffix-only fix (LIKE '%\_<id>.md' under vault/logs/sessions/) was bypassable: the attacker created vault/logs/sessions/2026-09-29_090000_vfySess7.md_nextSess9.md, allowed because the exact in-scope path acts as a startsWith prefix, and the suffix query selected it for session nextSess9. **Impact and priority.** Discloses the owner's session log (summary, body, next steps) about projects outside the attacker's scope. It also misfiles the owner's durable session record into an attacker-controlled path and overwrites the attacker's file there. No escalation beyond that one note. Needs a write-key holder whose scope covers the owner's earlier session note, or another way to learn the session id and win the ORDER BY. It also needs the owner to re-save that same session afterwards about a project outside the attacker's scope.

**Smallest fix.** Choose the re-save target only from a path that exactly matches the session's canonical log filename, and never from frontmatter. Anchor the full name (vault/logs/sessions/YYYY-MM-DD_HHMMSS_<sessId>.md) with GLOB, which is safe because sessionKey limits sessId to [A-Za-z0-9_-]. Otherwise create a new note. Optionally record the creating principal's key id and require it to match. Separately, treating exact expanded project paths as startsWith prefixes in allowed() lets a key create siblings such as <path>_x.md; consider matching exact paths exactly.

### 12. MCP search applies its SQL LIMIT before scope filtering, so out-of-scope notes change a scoped key's results

- **Severity:** low (likelihood low, impact low; confidence high)
- **Fingerprint:** `src/index.js:search:sql-limit-before-scope-filter`
- **Source:** `src/index.js:390` → `src/index.js:404` → `src/index.js:408`
- **Lower-trust principal:** Any valid scoped principal: a managed key, an OAuth token, or a web session minted from a scoped key.

The MCP search tool runs an FTS5 query ranked across the whole vault, truncates it to limit*3 rows, and only then drops rows the principal cannot read. A scoped key that can read a note containing term W can call search{q:W,limit:1}. If its own note comes back, fewer than 3 higher-ranked chunks contain W, so fewer than 3 hidden chunks do. If the result is empty while a control term from the same note still returns it, at least 3 chunks the key cannot see contain W and outrank it. Raising limit gives a rough count. This is an oracle for whether, and roughly how often, a term appears in notes the key cannot read. GET /app/api/search has the same pattern: it applies LIMIT 60 before the allowed() filter and then slices to 20. No hidden paths, titles or snippets are returned.

**Root cause.** Scope enforcement in search is a JavaScript allowed() filter applied after a globally ranked, LIMIT-truncated FTS result set (src/index.js:403-409, src/app.js:185-188). The principal's path prefixes are not part of the SQL WHERE clause.

**Bounded local reproduction.** Holder of a read-only managed key scoped to ['vault/projects/'] that can read vault/projects/alpha.md, which contains 'zebra marmot' plus 300 filler words.

1. Run agents/verify-15/artifacts/search_oracle.mjs in the sandbox. It loads the repository schema.sql into node:sqlite (FTS5), indexes dummy notes with the real parseNote/upsertNotes, creates a read key scoped to ['vault/projects/'] with the real createKey, and sends requests through the real worker fetch handler.
2. It runs four fresh-DB scenarios with the same anchor note: (a) no hidden notes; (b) 3 out-of-scope vault/private/h*.md notes containing 'marmot marmot'; (c) 3 out-of-scope notes containing an unrelated term; (d) 60 out-of-scope notes containing 'marmot marmot'.
3. Each scenario calls read_note on a hidden note (expected to be forbidden), search q=marmot with limit 1 and 2, search q=zebra limit 1 as a control, search with folder='vault/projects/', and GET /app/api/search?q=marmot via a cookie from /app/login.

**Conditions.** authentication level: Any valid scoped principal: a managed key, an OAuth token, or a web session minted from a scoped key. data state: A readable note must contain the probed term. For MCP search, at least limit*3 out-of-scope FTS chunks containing the term must outrank it (3 when limit=1). For /app/api/search, at least 60 must.

**Observed result.** read_note on the hidden notes returned 'forbidden' in every scenario. search{q:'marmot',limit:1} returned ['vault/projects/alpha.md'] in scenarios (a) and (c), and [] in (b) and (d). search{q:'marmot',limit:2} returned alpha.md in (b) and [] in (d), which gives a rough count of hidden matches. search{q:'zebra',limit:1} always returned alpha.md. With folder='vault/projects/', alpha.md was always returned. /app/api/search?q=marmot returned alpha.md in (a), (b) and (c), and [] in (d) with 60 hidden matches. The visible result therefore changes only when inaccessible notes contain the probed term.

**Impact and priority.** This is a one-term-per-query presence and rough-count oracle over out-of-scope notes. No hidden paths, titles, snippets or bodies are disclosed. The caller needs a readable note containing the probed term, which a write-scoped key could create in its own scope. At least limit*3 hidden chunks must also outrank it. A long readable anchor makes that easier, a short one harder.

**Smallest fix.** Move the principal's scope into SQL so that ranking and LIMIT cover only readable rows. When p.prefixes is non-empty, add one exact-prefix predicate before ORDER BY in the MCP search handler and in /app/api/search. Bind the prefix list as a single JSON array parameter matched through json_each (EXISTS (SELECT 1 FROM json_each(?) j WHERE substr(f.path, 1, length(j.value)) = j.value)). Do not use unescaped LIKE, and do not bind one or two parameters per prefix. expandScopes adds every indexed note path of a project: scope, so a per-prefix bind would pass D1's 100-bound-parameter limit and break search for large project scopes. Keep the JS allowed() filter as defense in depth. The same post-LIMIT pattern exists in list_notes (index.js:425-435). Fix it the same way for consistency.

### 13. Quadratic regex on skills.md rows makes every get_context and list_skills call burn CPU for all principals

- **Severity:** low (likelihood low, impact low; confidence high)
- **Fingerprint:** `src/skills.js:parseSkillsConfig:quadratic-lazy-trailing-whitespace-regex`
- **Source:** `src/index.js:479` → `src/index.js:354` → `src/skills.js:132` → `src/skills.js:26`
- **Lower-trust principal:** The attacker holds a write-role managed key (or an OAuth token or cookie derived from one) whose path scope covers vault/skills.md, for example a 'vault/' prefix. Read-only keys and keys scoped elsewhere cannot plant the line.

parseSkillsConfig (src/skills.js:26) runs /^([a-z0-9-]+):[ \t]*(\S.*?)[ \t]*$/ against every line of vault/skills.md. On a line of the form 'a:x' + N spaces + 'y', the lazy (\S.*?) grows one character at a time. At each step [ \t]*$ consumes the rest of the whitespace run and then fails on 'y', so one anchored match attempt costs O(N^2). Nothing in source caps the line or file length: update_note has no content limit, D1 rows allow about 2 MB, and the MCP body is read with req.json(). The parse is not cached. It runs again on every get_context (session start, any authenticated principal, any scope), every list_skills call, every GET /app/api/skills, and once inside PUT /app/api/skills. A principal whose write key covers vault/skills.md can commit one such line once. From then on every session start for the owner and every other key holder costs CPU that grows quadratically with the line length, until the file is fixed. Two sandbox runs measured about 0.6 s to 1.1 s per get_context-path parse at 32 KB, rising about 4x per doubling. The poisoned file still resolves the default row correctly, so nothing visibly breaks apart from latency, and failures once a line is long enough to exceed the CPU limit. Recovery means rewriting the file through update_note, through GitHub, or through a PUT /app/api/skills that completes. The PUT keeps only the existing header and re-renders rows from the submitted entries, which drops the poisoned row. It pays one slow parse of the existing file first, so it works only while a single parse stays within the deployed CPU limit.

**Root cause.** A lazy capture followed by an optional trailing-whitespace class and an end anchor (src/skills.js:26), applied with V8's backtracking engine to lines of unbounded length, and re-evaluated on every read request without caching.

**Bounded local reproduction.** Holder of a write key scoped to cover vault/skills.md who wants to degrade or block session start (get_context) and skills listing for the owner and every other key holder.

1. Run agents/verify-20/artifacts/skills-regex-growth.mjs with: python3 tools/sbx.py run BrainMCP/run-1 verify-20 skills-regex-growth.mjs --timeout 60 (Node 26 container, no network, target read-only at /target).
2. The harness imports parseSkillsConfig, resolveSkillsFor and skillsConfigEntries from /target/src/skills.js. It times each one (best of 2) on a dummy skills.md with a valid default row plus the poisoned line at 2k, 4k, 8k, 16k and 32k whitespace characters, and on a benign line of the same length as a control.
3. It also times a trimEnd-based fixed variant on the same input, and checks that the fixed variant returns the same entries as the original on ordinary rows.
4. In the native interface the attacker would call MCP tools/call update_note with path 'vault/skills.md' and the payload as content. Every principal's later get_context call would then run the measured path. This step was not performed against any deployment.

**Conditions.** authorization role: The attacker holds a write-role managed key (or an OAuth token or cookie derived from one) whose path scope covers vault/skills.md, for example a 'vault/' prefix. Read-only keys and keys scoped elsewhere cannot plant the line. data state: vault/skills.md contains one long line of the form '<slug>:<non-space>' + whitespace run + '<non-space>'. The file persists in git and D1 until someone rewrites it. environmental dependency: Cloudflare Workers runs V8's default backtracking irregexp engine, the same one measured locally in Node. The deployed per-request CPU limit is not set in wrangler.jsonc. It determines whether a given line length makes requests slow or fail outright, but not whether the cost is quadratic.

**Observed result.** Parent-promoted transcript (agents/verify-20/artifacts/skills-regex-growth.txt): resolveSkillsFor (the get_context path) took 2.89, 11.88, 44.22, 146.39 and 590.38 ms at 2048 to 32048 bytes. skillsConfigEntries took 2.75 ms up to 597.4 ms, and parseSkillsConfig 4.37 ms up to 602.74 ms, about 3.3x to 4.3x per doubling after the first step. A benign row of the same length stayed at or below 0.15 ms, and the fixed variant at or below 0.02 ms. The validator's own run reported the same shape at about twice the cost (resolveSkillsFor 1097.75 ms at 32 KB). On the poisoned file the default row still resolved correctly ([unslop must, principle-prove-it-works]). Larger sizes were not run. At about 4x per doubling the curve extrapolates to a few seconds at 64 KB, tens of seconds at 256 KB and about ten minutes at 1 MiB, but that is not measured.

**Impact and priority.** Availability only. Every principal's get_context, list_skills and Skills-tab request pays quadratic CPU on the shared Worker: about 0.6 s to 1.1 s per call at 32 KB, measured. Larger lines can be expected to exceed Workers CPU limits and fail session start for everyone. Nothing is disclosed or corrupted. The owner can recover by rewriting the file through update_note or GitHub, or through the Skills-tab PUT while one parse still fits the CPU limit. A writer to skills.md can already steer agents through must-load skills, so the marginal capability gained is denial of service. The attacker needs a write-role key whose scope covers vault/skills.md. That is a privileged configuration capability the operator hands out deliberately. One small write is enough after that, and the effect persists.

**Smallest fix.** Make row parsing linear. Trim each line, then match a pattern that has no ambiguous lazy capture followed by optional trailing whitespace. Optionally cap line or file length for vault/skills.md on write, and cache the parsed config per request or per D1 body hash. Add a regression check that parseSkillsConfig('a:x' + ' '.repeat(1e6) + 'y') completes in well under 50 ms. trimEnd also strips a trailing '\r', so CRLF rows that the current pattern rejects will start being accepted. That is a minor behaviour change and should be checked as intended.

## 6. Hardening notes

These are concrete improvements with no demonstrated boundary violation. They came from hunter results and were not independently validated.

- .github/workflows/deploy.yml: add a top-level `permissions: contents: read` block. Without one, GITHUB_TOKEN scope depends on repository settings not visible in source, and actions/checkout@v4 persists it into .git/config, where the esbuild/workerd install scripts run by npm ci can read it.
- .github/workflows/deploy.yml: move CLOUDFLARE_API_TOKEN/CLOUDFLARE_ACCOUNT_ID into a GitHub `environment` whose deployment branches are restricted to main, and add `environment:` to the job. workflow_dispatch currently lets any write-access user deploy an arbitrary branch to production.
- .github/workflows/deploy.yml: pin actions/checkout and actions/setup-node to full commit SHAs instead of the mutable @v4 tags.
- .github/workflows/deploy.yml: consider `npm ci --ignore-scripts` for the ui install (only fsevents has an install script there) to shrink the install-time code surface in the job that later holds the deploy token.
- .gitignore: add .env*, .dev.vars.*, *.pem, *.key and credentials* patterns. No such file is tracked today.
- src/app.js:13: anchor the cookie regex, e.g. /(?:^|;\s*)brain_session=([^;]+)/, so a cookie named xbrain_session is not read as the session.
- src/index.js / src/app.js / src/oauth.js: responses set no Strict-Transport-Security, X-Content-Type-Options or Referrer-Policy headers, and TLS enforcement for the custom domain depends on dashboard settings (Always Use HTTPS) not visible in source.
- src/github.js:18,48,85,105: GitHub error bodies (up to 300 chars) are relayed to MCP and app callers. Consider logging them server-side and returning only a status code.
- /health (src/index.js:734-752) is anonymous and returns the live tool_calls buffered count, the notes count and the unsaved_sessions count. A polling outsider can watch the owner's tool-use activity and note growth in real time. Consider requiring a key or returning only {ok:true}. No note content, paths or principal data are exposed, so this is not reported as a finding.
- computeHygiene counts.notes and counts.links (src/app.js:39-42,113-114) are whole-brain totals even in a scoped report. They duplicate what /health already exposes anonymously, so there is no extra disclosure, but they could be scoped for consistency.
- normalizeScopes (src/auth.js:40-51) accepts path scopes without a trailing '/', and allowed() is a plain startsWith, so an admin-typed scope 'vault/logs' also matches 'vault/logs-private/...'. The key editor's area list always ends in '/'. Consider requiring a trailing '/' or an exact .md path.
- search limit is not clamped below (src/index.js:391). limit:-1 binds LIMIT -3, which SQLite treats as unlimited, so the whole matching FTS set is fetched and then filtered. There is no disclosure (the output is scope-filtered and slice(0,-1) trims it), but clamp with Math.max(1, ...).
- get_context computes skillsPayload (src/index.js:354) before the slug access check, and skillsPayload reports on_demand and unresolved names from the unscoped skills config for the requested slug. This is covered by the readSkillsConfig fingerprint's fix.
- The oauth-branch role fallbacks default to 'admin' (src/auth.js:102 tok.role || 'admin', src/oauth.js:127-129 role || 'admin', schema.sql:51 DEFAULT 'admin'). No current insert path produces a null role, but a legacy or migrated row would resolve as whole-brain admin. Defaulting to 'read', or rejecting the row, fails closed.
- timingSafeEq (src/auth.js:19-24) returns early on length mismatch, which reveals BRAIN_TOKEN's length. That is negligible for a high-entropy secret, but comparing SHA-256 digests with a constant-length compare removes it.
- Credentials derived from BRAIN_TOKEN are stored with key_id NULL and have no revocation path. Rotating BRAIN_TOKEN does not invalidate them, so break-glass recovery after root exposure means manually deleting oauth_tokens rows. This is covered as a variant in the key_id candidate.
- Login CSRF: POST /app/login accepts a cross-site top-level form POST, and the SameSite=Lax cookie is set on that navigation response. That lets an attacker holding any valid key swap the victim's session for their own scoped session. Add an Origin check (Origin must equal url.origin) on /app/login and on all /app/api/* mutations.
- POST /app/api/keys and /app/api/keys/revoke parse bodies with req.json() without requiring Content-Type: application/json, so text/plain form posts are accepted shape-wise. Require application/json, which forces a CORS preflight, as defense in depth against same-site sibling origins.
- NoteView disables react-markdown's default urlTransform. javascript: is currently neutralised only by React 19's sanitizeURL. Restore defaultUrlTransform and allow only the brain: and brain-dead: schemes, so safety does not depend on the React version.
- There is no logout endpoint, and re-login does not delete the previous session row. Add POST /app/logout that deletes the current token row and clears the cookie.
- Add a restrictive Content-Security-Policy (script-src 'self'; object-src 'none'; frame-ancestors 'none') for the SPA assets to contain any future HTML-sink bug.
- isProjectSlug (src/auth.js:26) allows '.' and '..', so an admin-created 'project:..' scope expands to 'vault/projects/../' (and '...md'). Require slugs to start with an alphanumeric and reject dot-only slugs.
- Expanded exact-file prefixes and admin path scopes without a trailing '/' also match sibling names that share the string prefix (for example 'vault/projects/alpha.md' matches 'vault/projects/alpha.mdx', 'vault/logs' matches 'vault/logsX/'). The boundary-aware allowed() in the remediation closes this.
- Any writer can put 'project: <other-slug>' in frontmatter of a note it controls (parse.js:98). This files the note into another project's expansion and its get_context recent_sessions view. It widens other holders' view of attacker content rather than the attacker's reach; consider restricting expansion to notes under project-owned folders or checking the writer's scope for the named project.
- upsertLocal (src/indexer.js:47-49) indexes the caller's unnormalized path, so a '..' write leaves a phantom D1 row (for example 'vault/logs/../rules/beta.md') that disagrees with the real repo path until a full reindex.
- src/hook.js:293-327: if ~/.claude/settings.json fails to parse (for example a stray trailing comma), the installer falls back to settings = {} and overwrites the file. That silently drops the user's permissions.deny, sandbox and other hook settings. Abort instead of overwriting.
- src/hook.js:308-322: stale-hook cleanup deletes any PostToolUse hook whose command contains 'post-tool-use.sh' and any SessionStart hook containing 'session-start.sh', including unrelated user-owned guard hooks. Match the exact installed paths.
- src/hook.js:26: the hook shell-sources the credentials file on every tool call ('. "$CRED"'), and the installer writes BRAIN_KEY unquoted with printf. Parse KEY=value without eval so a malformed file cannot execute.
- src/index.js:852 / src/hook.js:22,333: url.origin goes unescaped into double-quoted shell, and the WHATWG URL parser keeps $( ) in hostnames (observed: https://a$(id).test). The requesting client controls it, so there is no cross-principal impact today. Emit origin from a configured allowlist or single-quote it.
- src/hook.js:37-50: the hook reads BRAIN_URL from the environment and flushes the key there. That is same-user controlled, but pinning the installed origin, with an env override only for testing, avoids sending the key to a stray BRAIN_URL exported for another tool.
- The /skills/install.sh output has no integrity binding: no per-file digest, signature or pinned commit sha. Its content is whatever repo HEAD holds at request time, so anyone with skills/ write scope changes what every later installer run executes. Consider pinning the commit sha in the script header and listing the last committer per skill.
- The installer auto-marks every *.sh file executable. Restricting this to an allowlist such as skills/<name>/scripts/*.sh, or requiring an explicit manifest, would narrow what a skill writer can push as executable onto client machines.
- Scope prefixes are not required to end with '/'. A key scoped 'skills/foo' also matches 'skills/foobar/...' in allowed(), and therefore in the installer filter. This belongs to the path-scope unit and is noted only as hardening here.
- e.text() decodes every tar entry as UTF-8 before re-encoding to base64, which corrupts binary skill assets. This is not a security issue, but it means binary files are not shipped byte-for-byte.
- POST /ingest/tool-calls (src/index.js:822-834) gates on canWrite(p) only, so any write/admin key regardless of path scope can append to the global tool_calls buffer; consider whether telemetry ingest should be scope- or principal-constrained (noted as hardening, not a reported finding, since no cross-principal read/impact was established within this unit).
- recordRollup is also reachable on the nightly cron with a synthetic {role:'admin', prefixes:[]} principal (src/index.js:901), confirming the intended caller for the global routes is an unscoped admin; the fix should preserve that path.
- src/index.js:646-665 ingestToolCalls stores no key_id or principal and ignores the caller's scopes. Any write-role key, even one scoped to one project, can append forged records into any session and any past day, including the owner's existing R2 objects (observed locally). Store p.keyId/p.name per row and, for scoped keys, restrict project/session attribution.
- src/index.js:676-697 rollUpToolCalls SELECTs day<today and later DELETEs day<today without a bound on id. Rows with a past ts that arrive between the two, such as hook spools flushed after up to 7 days offline, are deleted without reaching R2. Delete by the max id that was read.
- src/index.js:650 accepts any YYYY-MM-DD prefix, so future-dated rows (e.g. 9999-12-31) are never drained from D1 (observed). Clamp the day to [today-8d, today].
- src/index.js:661 slices JSON.stringify(r) to 8000 bytes, which stores invalid JSON lines in R2 (observed). Drop or trim fields before stringifying instead.
- src/hook.js:62-73 redaction misses literal bk_ managed keys not preceded by 'bearer' (e.g. 'BRAIN_KEY=bk_...') and brain_session=<token> cookie values. Add patterns for \bbk_[A-Za-z0-9_-]{16,} and brain_session=\S+. The server treats itself as a buffer, not a scrubber.
- src/index.js:755-779 webhook has no X-GitHub-Delivery replay dedup and does not check payload.repository.full_name against env.REPO. A replayed or foreign-repo signed delivery can re-delete index rows until the nightly reindex. It needs the secret, so this is low.
- src/index.js:771 sets meta needs_reindex when more than 40 paths change, but nothing reads that key. Pushes over 40 files leave the rest unindexed until the nightly cron.
- GET /skills/install.sh (src/index.js:788) downloads and decompresses the full repo tarball on every request from any authenticated principal, including read keys. That spends the shared GitHub PAT rate limit used by all writes. Cache the tarball per commit sha.
- The POST /mcp batch has no length cap. Even without GitHub calls, each message runs its own D1 queries, for example check_brain/computeHygiene scanning all session notes.
- /skills/install.sh fetches and decompresses the whole repo tarball on every authenticated request. Caching by branch head sha would remove repeated upstream and CPU cost.
- /ingest/tool-calls ignores key path scopes, so a key scoped to one project can file telemetry under any project or cwd value. Records should store key_id and be checked against the key's scope.
- Anonymous /health exposes the telemetry buffer count and last_rollup details. That is useful to an attacker tracking buffer growth.
- The webhook path caps indexFromGitHub at 40 paths per push (index.js). This is a working fan-out control that the other GitHub-backed routes lack.
- /app/api/graph (app.js:190-208) and /app/api/check (app.js:209-211) scan all of notes and links for every request, including scoped read sessions, and filter in JS. Cost per request is O(notes+links) and does not batch, so it grows only with request rate. Pushing scope into SQL (WHERE path LIKE prefix || '%' for each expanded prefix) would make cost proportional to the caller's scope.
- check_brain and /app/api/check return whole-brain counts.notes and counts.links to scoped keys. That disclosure belongs to the peer-owned hygiene existence oracle and is not duplicated here.
- computeHygiene builds byNoExt/byBase maps over every note path in Worker memory for every message. Memory is per-invocation and bounded by vault size, but a per-request message cap would bound it as well.
- The /app/api/search fixed LIMIT 60 (app.js:183-186) cannot be changed by the caller and is bounded.
- sessionNote (src/index.js:68,73) puts the project slug and surface into YAML frontmatter unescaped, so newline injection can add arbitrary frontmatter keys. This gives no authority beyond update_note on the same allowed path, but applying yamlStr and the isProjectSlug charset to both would stop templated notes from taking on attacker-chosen type/project/session_key.
- Decision blocks in vault/logs/decisions.md carry no writer provenance. get_context(project) attributes them by free-text match on '[[projects/<slug>]]' (src/index.js:371), so a vault/logs/-scoped writer with no project access can put decisions into any project's recent_decisions (reproduced locally). Recording the writing key id and filtering on the structured Project line would limit cross-project attribution.
- save (src/index.js:530-533) and patchProjectNote read decisions.md and the project note via getFile, then commit the full rewritten file with multiCommit on top of a separately read HEAD (src/github.js:72-107). A decision appended concurrently between the two reads is silently dropped (lost update). update_note uses the freshly read sha instead of the caller-supplied expected_sha its description promises (src/index.js:482-483).
- save_session accepts duplicate paths in files[]. D1 indexes the last entry (src/index.js:494) while the committed git tree outcome depends on GitHub's handling of duplicate tree entries, so the index can diverge from git until the next reindex.
- A null member in a JSON-RPC batch makes handleRpc throw outside any try (src/index.js:600,887), which turns into an uncaught Worker 500 instead of a -32600 error for that member.
- The SPA and API responses set no Content-Security-Policy, X-Frame-Options or frame-ancestors anywhere in source (ui/index.html, ui/public, wrangler.jsonc, src/app.js). A script-src/connect-src policy would block both the graph tooltip injection and exfiltration of a minted key.
- search and list_notes accept a negative limit, which makes SQLite run LIMIT with no bound (src/index.js:391,425). Results are still scope-filtered; clamping limit to at least 1 would bound per-call D1 work.
- src/index.js sessionNote writes surface into YAML without yamlStr (line 73), which lets a caller inject frontmatter keys. Passing surface through yamlStr or a [A-Za-z0-9._-] allowlist would remove the vault/logs/-only variant of the graph chain.
- The webhook writes meta 'needs_reindex' when a push changes more than 40 notes (src/index.js:771), but nothing reads it, so the extra notes stay unindexed until the next cron run. Have the cron or /health act on it.
- For files over 1 MB, getFile in the webhook path relies on the Contents API 'content' field, which GitHub leaves empty. indexFromGitHub would then index such notes as empty while fullReindex indexes the full body. That is inconsistent but not a security issue.
- fullReindex holds the whole repo tarball and every parsed note in memory at once (src/index.js:27-31). Repo growth, including large non-.md files committed by writers, scales Worker memory per run. Consider streaming tar entries.
- get_context sends the hint 'Binding rules above are MANDATORY for this project' (index.js:384-386) even when no project slug was given and no binding_rules field exists. Send it only when binding_rules is present.
- check_brain broken_links[].dst (app.js:100-108) echoes wikilink target text written by any scoped writer, and INSTRUCTIONS (index.js:152) tell agents to 'fix anything it flags'. Return dst as structured data with the src path's writer scope, or cap and escape it.
- decisionBlock (index.js:92-97) keeps raw newlines from the decision text. A writer can embed '\n### [date] ... [[projects/<other>]]' and make get_context's split at index.js:370 return extra forged blocks tagged with other projects. Strip or escape newlines and '### [' in decision and rationale.
- The consent page (oauth.js:101) is served with only Content-Type. Add Content-Security-Policy: frame-ancestors 'none' and X-Frame-Options: DENY. No clickjacking finding, because granting requires typing a non-ambient key.
- PKCE is optional (oauth.js:139) and code_challenge_method is ignored. OAuth 2.1 requires PKCE: reject authorize requests without an S256 challenge.
- /token never compares client_id with the code row, and compares redirect_uri only when the request includes it (oauth.js:143). Require both.
- Code and refresh single-use is SELECT followed by DELETE (oauth.js:136-138, 151-153), which is not atomic across concurrent D1 requests. Use DELETE ... RETURNING and treat zero rows as invalid_grant.
- Hidden-input escaping (oauth.js:92) handles only '"'. Use full attribute escaping (&, <, >, ", ') so values round-trip exactly.
- new URL(redirect_uri) (oauth.js:114) throws on an invalid URI after the code row is already inserted, which leaves an orphan code and an uncaught 500. Validate before inserting.
- Expired oauth_codes and oauth_tokens rows are never garbage-collected. Add cleanup to the nightly cron.
- Pin "preview_urls": false (and "workers_dev": false once the GitHub webhook and ~/.config/brain-mcp/credentials MCP_URL move to the custom domain) in wrangler.jsonc. Wrangler 4.121.0 otherwise re-enables workers.dev on every CI deploy, overriding any dashboard toggle.
- workers.dev is a Public Suffix List entry, so <subdomain>.workers.dev is the registrable site. Every other Worker and preview URL on the same account subdomain is same-site with brain-mcp.<subdomain>.workers.dev, and the SameSite=Lax brain_session cookie (src/app.js:144) gives no cross-site protection between them. - Every hostname derives its origin from the Host (OAuth issuer/endpoints at src/oauth.js:27, hook installer BRAIN_URL at src/index.js:852 / src/hook.js:22).
